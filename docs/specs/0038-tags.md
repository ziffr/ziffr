# 0038 Tags: free words on Metrics, to find and group them

**Status:** draft. **Ticket:** #653 (the owner's decision, 2026-11-22); the tracking issue is #653 and its sub-issues are labelled `spec:0038`.

## Problem Statement

A Workspace with 15 Metrics finds them by name. One with 150 does not. People want to say "these are the finance numbers", "these go into the Monday review", "these belong to the Berlin shop", and then see, search and show exactly those. Today the only ways to group Metrics are a dashboard (a picture, made by hand, one at a time), a Group (which groups people, not Metrics) and the Metric Catalog's industry keys (fixed by Ziffr, only on catalog entries). A person who wants "all the Metrics about cost" scrolls and remembers.

## Solution

A **Tag** is a free word that people put on Metrics, such as `finance` or `weekly review`. Anyone who may change a Metric's description adds and removes Tags on it; Owners and Admins rename, merge and delete Tags for the whole Workspace.

1. **Tags on a Metric:** a Tags field on the Metric page, with the Workspace's Tags offered as you type and new words accepted as they are.
2. **Finding:** the Metrics list filters by Tag; Search (⌘K), the API and the MCP Server find by Tag; a Metric's Tags show on its page, in lists and in what programs read.
3. **Dashboards:** a widget that takes several Metrics may take **all Metrics tagged X** instead of a fixed list. Each viewer sees the tagged Metrics they may see themselves.
4. **Packs:** a Metric Catalog entry in a Pack may carry Tags; a Metric made from it gets them.
5. **Keeping order:** Owners and Admins rename, merge and delete Tags on a Tags page in Workspace settings.

Tags are about Metrics only. Dashboards, decks and Workflows get none for now.

## User Stories

1. As a Member who may edit a Metric, I want to add a Tag by typing a word, so that I group Metrics without asking anyone.
2. As a Member, I want the Metrics list to show only the Metrics with a Tag, or with two Tags together, so that I find "finance and monthly" at once.
3. As a Member, I want Search to find "finance" and offer its Metrics, so that I reach a group without leaving the keyboard.
4. As someone asking an assistant, I want "list the Metrics tagged cost" to be one call, so that it does not read every Metric to find out.
5. As a dashboard's owner, I want a widget that shows every Metric tagged `shop`, so that a Metric tagged later appears without my editing the dashboard.
6. As a viewer of such a dashboard, I want it to show only Metrics I may see, and to learn nothing about the ones I may not, so that a Tag never opens a private Metric.
7. As an Owner or Admin, I want to rename `Finanz` and `finance` into one Tag, and to delete a Tag nobody wants, so that the words stay tidy.
8. As someone writing a Pack, I want my Metric Catalog entries to carry Tags, so that a shop's Metrics arrive grouped the way the Pack's dashboard expects.
9. As a Guest, I want to use the Tags I can already see, but not to make new ones, so that the words of the team stay the team's.
10. As an Owner, I want Tag names unreadable in a stolen dump like Metric names, so that a Tag does not tell what the Workspace measures.

## Implementation Decisions

### Words

- **Tag** is new (glossary): a free word of a Workspace that people put on Metrics to find and group them. _Avoid_: label, category, folder, hashtag, keyword.
- **Not a Group:** a Group is a set of people that things are shared with; a Tag never shares anything and never changes who sees what.
- **Not an industry or segment key:** those belong to Metric Catalog entries, are fixed by Ziffr and only suggest entries to a Workspace of a certain kind. A Tag is on live Metrics, made by people, and means whatever the Workspace says. A Metric made from a catalog entry carries no link to its industries; it may carry Tags (below).
- **Not a Breakdown's labels:** those are rows inside one value ("Germany", "France"); a Tag is on the Metric.
- The glossary's **Metric Description** gains "its Tags"; **Search** says that it finds a Metric by its Tags.

### What a Tag is

- **Per Workspace.** A Tag belongs to one Workspace, never to the Installation or a person, and two Workspaces may use the same word without any link. It is stored as a row (`tags`: the Workspace, the name, who first used it and when) and a link table (`metric_tags`: the Metric and the Tag), so a rename is one change and a merge is one move.
- **Normalised by the core** (the same function in the app, the API and the Pack checks): Unicode NFC, leading `#` removed, surrounding spaces removed, runs of spaces and other white space become one space. Two names are the same Tag when they are equal ignoring case (`Finance` and `finance`); the Tag keeps the spelling it was first written with, and the Tags page lets an Owner or Admin change it. No other folding: `Finanz` and `finance` are two Tags until someone merges them.
- **Allowed words:** 1 to 32 characters after normalising; plain text only: no control characters, no comma (it separates Tags when typed or pasted), no line breaks, no HTML (shown as text everywhere, never as markup). Tags are Workspace text that reaches AI assistants, so they pass the assistant-words filter of spec 0030 where Packs bring them.
- **Limits** (constants beside the other limits of spec 0029, not a Size): at most **10 Tags per Metric** and **200 Tags per Workspace**. A Tag with no Metric left is removed by the core (nothing lingers in the list), so 200 counts words in use. The limits are low on purpose: a Tag list that needs more is a folder tree in disguise, and Ziffr does not build one. Reaching a limit says so in words and names what to do (merge or delete Tags).
- **Sealed** with the Workspace Key (spec 0028, ADR 0012): a Tag name says what the Workspace measures as much as a Metric name does, so the column is born sealed, with a blind index (HMAC of the normalised, lower-cased name) for "one Tag per name per Workspace". Step 1 of spec 0028 gains "Tag names" in its list. Filtering, sorting and Search over Tags run in the core over opened rows (at most 200 per Workspace), never in SQL.
- **Versions:** a Metric's Tags are part of its Metric Description, so adding or removing one is a change in the Metric's Versions with its author and time. A Version keeps the Tag names as they were then; restoring a Version puts those names back, matching Tags by name and making any that were deleted meanwhile, within the limits. Renaming, merging and deleting a Tag are Workspace acts, not Versions of each Metric.
- **Audit Log:** `tag.renamed`, `tag.merged` and `tag.deleted` with the names and how many Metrics they touched (as a number the actor sees, below), since one act changes many Metrics at once. Adding a Tag to one Metric is an edit with a Version, not an Audit Log event: the Audit Log is for who may see or do what.

### Who may do what

| Who | Tags on a Metric | The Tags page |
| --- | --- | --- |
| Owner, Admin | add and remove on any Metric they may change | rename, merge, delete |
| Member | add and remove on a Metric they own or are an Editor of | sees Tags and counts, changes nothing |
| Viewer, Guest with a Viewer Share | none | none |
| Guest who is an Editor of a Metric | add and remove **only Tags they can already see**; no new words | none |
| Access Key with `metrics:write` | as the key's creator, through `create_metric` and `update_metric` | none |

- **Anyone who may edit a Metric may tag it** is the owner's rule; the Guest line follows Ziffr's rule that Guests create nothing.
- **Renaming, merging and deleting are not in the API or the MCP Server.** They change many Metrics at once and are exactly what a prompt-injected assistant would be asked to do to tidy away a Tag; the page is enough. Programs add and remove Tags on Metrics their key may change, like any other field.
- Every change goes through `packages/core` functions that take the Actor first and check the Workspace and permissions (AGENTS.md rule 2). Server actions only call them.

### What a person sees of Tags: derived from Metrics they may see

- **Tag names are Workspace-wide rows, but nobody is shown a Tag except through a Metric they may see.** A person sees a Tag if at least one Metric they may see carries it; their count is the number of such Metrics. The suggestions while typing, the filter list, Search, the Tags page, `list_tags` and the dashboard widget all use this one rule, from one core function (`visibleTags(actor)`), so a Tag name alone never reveals that a private Metric exists or what it is about.
- **The Tags page for Owners and Admins** lists the Tags they see by this rule, with counts of the Metrics they see. A Tag only on Metrics the Admin cannot see is not listed to them. Rename, merge and delete act on the whole Tag, hidden Metrics included: a person who sees the Tag through any Metric may rename it for everyone, and deleting it removes it from every Metric, which the confirmation says ("removes this Tag from 7 Metrics you can see and any you cannot"). The words "any you cannot" appear only when the core knows that hidden Metrics carry it, and then say nothing more.
- **Merging** `A` into `B` needs both visible to the person. Hidden Metrics carrying `A` carry `B` afterwards; the person learns nothing about them.
- **Typing a word** that exists only on hidden Metrics attaches the existing Tag, silently, so the word is the same Tag Workspace-wide. This leaves one small, accepted signal: a Workspace at its 200-Tag limit refuses a new word but accepts one that exists, so a person at the limit could learn that a word is used somewhere, never where or on what. The same holds for renaming to such a word (the Tags are merged, the Tag shows its first spelling) and for the spelling it then shows: a person learns that a word is used somewhere, and how it was first written, never where or on what. The threat model lists it under accepted risks.
- **Archived Metrics** keep their Tags and count in lists under Archived only. A Tag whose Metrics are all archived is still a Tag.
- **Deleting a Metric** removes its links; the core deletes a Tag left with none.
- **Never sent:** a Tag reaches a View Link page, a Feed, a Webhook, an Alert or a Delivery only where the Metric itself is shown there and the Tag is part of what that thing shows today; none of them gains a Tag field in this spec.

### The Metrics list, Search, API and MCP

- **Metrics list:** a **Tag** filter with the visible Tags and their counts. Picking several shows Metrics that carry **all** of them (narrowing is the use: "finance" and "monthly"); the filter is in the address, so a filtered list can be bookmarked and shared (people see only what they may). Tags show as small chips on each row, at most three and "+2".
- **Search (⌘K):** a word equal to a visible Tag offers **Tag: finance (7 Metrics)**, which opens the Metrics list filtered by it; Metrics are also found by their Tags after name matches, shown with the Tag that matched. Search still finds only what the person may see.
- **API and SDK:** every Metric read gets `tags` (names, sorted); `GET /api/v1/metrics?tag=finance&tag=monthly` filters (all must match); `GET /api/v1/tags` lists the Tags the key's creator sees with their counts; creating and updating a Metric accept `tags` (the whole set, at most 10), which replaces the Metric's Tags. The OpenAPI reference is generated, not edited.
- **MCP:** `list_metrics` gets `tag` (one or more, all must match) and returns `tags` on every Metric; a new read-only tool `list_tags`; `create_metric` and `update_metric` accept `tags`; `find` also matches Tag names, after Metrics whose name or period matched, marked `matched_by: "tag"`. The tool descriptions say that Tag names come from the Workspace and are data, not instructions.
- **Programs and assistants** need the scope they already need for the Metrics: reading Tags needs `metrics:read`, setting them `metrics:write`. No new scope.

### Dashboards: all Metrics tagged X

The question: Dashboard Templates (spec 0014) and Slots take Metrics one by one, and sharing a dashboard gives view access to every Metric on it. A Tag that fills a widget changes with time, so who sees what has to be settled first.

- **A Tag source for widgets that take several Metrics** (the "one or more" Slots of small multiples and the like): a widget holds either its fixed list or **All Metrics tagged X**. It is resolved every time the dashboard is drawn.
- **Each viewer sees only what they may see on their own.** The Metrics a Tag widget draws are those tagged X that the viewer may see **through their own role, Shares and Groups**, not through the dashboard's Share. The rule "sharing a dashboard gives view access to every Metric on it" holds for the Metrics fixed on the dashboard, not for a Tag widget's: otherwise tagging a private Metric would publish it to everyone who sees the dashboard. Two viewers may see different Metrics in the same widget; neither is told about the others (no "3 hidden"). With none, the widget says "No Metric tagged X that you can see."
- **Same limits as a fixed widget:** it draws at most the number the widget draws today, ordered by name, and says "and 4 more" with a link to the Metrics list filtered by the Tag.
- **A Tag renamed** is followed; merged, it follows the target; **deleted**, the widget says the Tag was removed and keeps its place, empty, until its owner changes it.
- **Who may set it:** the dashboard's owner or an Editor, who sees the Tag by the rule above.
- **View Links and decks:** a View Link shows people without an account what the link's maker chose, so it needs a fixed list: making a View Link of a dashboard with a Tag widget offers **Fix the list** first, which replaces the Tag by the Metrics the maker sees now, and says so. Adding such a widget to a deck, and taking a Snapshot, record the Metrics drawn at that moment for the person doing it, as for a fixed widget; they do not follow the Tag afterwards.
- **Dashboard Templates:** saving a dashboard with a Tag widget as a template turns it into a **one or more Slot called "Tagged Metrics"** (the saver may rename it, and is told the whole Workspace reads the name); a template names no Tag, since Tags belong to a Workspace and a Tag's name is shown only through Metrics a person sees, while a template is read by everyone, `list_templates` included. Using a template, a "one or more" Slot is filled by ticking Metrics **or by choosing a Tag** ("All Metrics tagged…"), which makes a Tag widget. A dashboard made from a template stays an independent copy (spec 0014).
- **API and MCP:** widgets are added through `add_widget` and `update_widget` with the Metrics as today; a Tag source in them is a later addition (below).

### Packs

- **A Metric Catalog entry** (`ziffr.metric/1`) may carry **`tags`**: up to 5, normalised and checked as above, and by the assistant-words filter. Unknown fields are refused by older Ziffr versions, so a Pack that uses Tags says so in its `ziffr` minimum version, as every Pack format change does; no `/2` is needed for one optional field.
- **Installing** a Pack still creates nothing (spec 0030): no Metric and no Tag. The Pack's page and Preview show an entry's Tags as chips.
- **A Metric made from an entry** (from the Metric Catalog or by **Set up from this Pack**) gets the entry's Tags, matching existing Tags by name and making the others, within the limits; if a limit is reached the Metric is still made and the page says which Tags were left out. Like the rest of a catalog copy, there is no link back: changing the entry later never changes the Metric.
- **Export as Pack** carries the Tags of the Metrics a person picks, shown in the Preview and removable there, and never a Tag of a Metric they did not pick.
- Ziffr's own catalog entries and starting Packs keep their industry keys; giving the starting Packs Tags is a content change for later.

### Performance and docs

- 200 Tags and a few thousand Metrics are opened and filtered in the core in a few milliseconds; the first database test measures a Metrics list with 1,000 Metrics and 10 Tags each.
- **Docs:** the user guide chapters Metrics, Dashboards, Workspace settings and Packs; `docs/guides/api.md` and `docs/guides/mcp.md` through their generated references; `docs/guides/packs.md` for creators; the threat model entry above.

## Testing Decisions

- **Normalising, pure:** NFC, `#`, spaces, case-equal names, comma and control characters refused, 32 characters, the same function used by the Pack checks.
- **Visibility, the main test** (`tags.db.test.ts`): a table of people (Owner, Admin, Member with a Share, Group member, Editor, Viewer, Guest, a person with no Share) against Metrics (private, shared with them, shared with a Group, archived), checking `visibleTags`, counts, the filter, Search and `list_tags`: nobody gets a Tag name or a count that only hidden Metrics carry. Rename, merge and delete as an Admin who cannot see some tagged Metrics: they act on all of them, the answers say nothing about the hidden ones.
- **Who may do what:** each row of the table above; a Guest Editor cannot make a Tag; no API route or MCP tool renames, merges or deletes (a test lists the routes and tools, as spec 0037's does).
- **Limits and lifecycle:** the 11th Tag on a Metric, the 201st Tag, a Tag removed with its last Metric, restore from a Version with a deleted Tag, merge while a Metric carries both.
- **Sealing:** a dump holds no Tag name (spec 0028's dump test gets the words); the blind index finds `Finance` for `finance`; another Workspace's index differs.
- **Dashboards:** a Tag widget for two viewers with different sight; a Metric tagged after the dashboard was shared is not opened to its viewers; Fix the list; Snapshot and deck record the Metrics of the person doing it; template round trip (Tag widget to Slot and back through a Tag).
- **Packs:** `@ziffr/pack check` and the server agree on a hostile table (11 Tags, a comma, a 33-character Tag, markup, an assistant-aimed sentence); a Metric made from an entry gets its Tags; Set up at the Tag limit still makes the Metric and says what was left out; Export as Pack round trip.
- **Pages** tried in the running app (Metric page, list filter, Search, Tags page, a Tag widget), and the user guide chapters updated.

## Out of Scope

- Tags on dashboards, decks, Workflows, Findings or Contacts. A later spec may add them; they would reuse the same Tag rows and the visibility rule above, one link table per kind.
- Nested Tags, Tag colours, Tag descriptions, "any of these Tags" filters, saved filters.
- Tag rules that apply themselves ("tag every Metric named *revenue*"), and Tag-based Shares or permissions: a Tag never changes who sees what.
- Setting a Tag source on a widget through the API or MCP.
- Tags in Feeds, Webhooks, Alerts and Deliveries.
- Tags in the built-in Metric Catalog and the five starting Packs.

## Decisions (2026-11-22, by the owner)

1. Anyone who may edit a Metric adds Tags as free words; Owners and Admins rename, merge and delete them.
2. Tags filter the Metrics list, Search and the API and MCP; a dashboard can show all Metrics tagged X; Packs can bring Tags with their Metric Catalog entries.

Proposed in this spec, open to change: per Workspace, case-insensitive names with spaces collapsed; 32 characters, 10 per Metric and 200 per Workspace; Tags shown only through Metrics a person may see; names sealed; Guests only use Tags they see; several Tags in a filter mean all; a Tag widget shows each viewer only what they see on their own, so a dashboard's Share never opens a Metric through a Tag; View Links need a fixed list; templates turn a Tag widget into a Slot; renaming, merging and deleting not in the API or MCP.
