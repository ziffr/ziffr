# The demo opens to visitors' changes on a demo-only Installation

On an Installation that is a public demo and nothing else (`ZIFFR_DEMO_ONLY=1`), and only where its setting `ZIFFR_DEMO_CHANGES` is on (off by default), anonymous visitors may try the everyday work in the one shared demo Workspace: values, dashboards, decks, Snapshots, Metrics, Questions and Tasks, and sharing among the demo's made-up people. What they change is seen by every visitor, is bounded by limits, and is gone at the next **Demo Reset**, which runs every 15 minutes after a change. Everything that reaches outside the demo (a message, a Webhook, a link, a key, an upload) and every Workspace setting that every visitor would feel stays refused, with the sentence it always had. Anywhere else the demo stays read-only as spec 0029 made it, and so does a demo beside real Workspaces. The database stays the boundary: a write to the demo passes only for a table on an allow-list, from a visit of the current Generation, within the limits, and the core classifies every server action in the same way. The owner decided this on 2026-11-23; spec 0051 has the details. This changes the decision of spec 0029 ("Demo Mode becomes read-only") for demo-only Installations and amends the consequences of ADR 0005.

## Considered Options

- **Keep the demo read-only (spec 0029):** rejected. A demo where nothing can be done does not show what using Ziffr is like, and the owner found it stale for exactly that reason. The reasons for read-only still hold, which is why this is bounded to a demo-only Installation and to a window of 15 minutes.
- **A private copy of the demo per visitor (spec 0051, option B):** rejected for now. Every copy is a full seed (eighteen months of values and the Snapshots the core computes), so a burst of visitors is a burst of seeds, and storage grows until a clean-up runs. The demo is one Workspace by its id in about 60 places of the core and in the seed's functions, so a copy needs a Workspace kind, a cheaper guard test than a lookup on every write of every Installation, every seed function rewritten in a new migration, and people who belong to many Workspaces. And an anonymous way to make Workspaces is a way to make work for the server at will, close to a trial without the sign-in that bounds trials.
- **A trial seeded with the demo's numbers (option C1):** not now, and not excluded. It gives a space of one's own to people who sign in, bounded by the Trial Limits, and needs the same seed rewrite as B. It is a spec of its own if visitors ask.
- **Shared reading and private writing (option C2):** rejected. Every read of the core would need a second visibility rule for the demo, exactly where "whatever you return must be something the person may see" is hardest to keep, and a mistake would show one visitor's words to another.
- **Moderation by words:** rejected as weak against anyone who means it. The 15 minutes, the kept seeded words, short plain text and the limits bound the harm instead.
- **Turnstile once per visit before its first change:** planned (spec 0051, ticket 12) and then not built: the owner decided on 2026-11-24 to rely on the limits first. A check per visit is a small step for a person and a large one for a script, and it is the first lever if abuse shows.

## Consequences

- **Visitors see each other's work for up to 15 minutes**, including what a stranger types, and a visitor's work can vanish while they look at it. The line on every page says what is shared and when the demo starts fresh, and a page open at a reset follows the demo's own dashboards and decks to their new versions. The owner accepted this.
- **A visit is free to mint**: its id is 128 random bits in a cookie, unsigned, so only the counts per network address, per network and for the whole demo hold against a script, and a group of networks can use up the demo's budget for a window (the demo is then read-only until it starts fresh). Accepted, since nothing outside the demo is hurt and reading is never limited. The address is counted only as a keyed hash under `ZIFFR_DEMO_ADDRESS_KEY`, from a trusted proxy header, so an Installation needs that key and `ZIFFR_PROXY_HOPS`.
- **Anonymous writes land in the database of the Installation**, which is why it must be a demo-only Installation with no real Workspace, and why the setting is in effect only there. An Installation with real Workspaces keeps today's read-only demo.
- **The seed's words and a showcase are kept** (the dashboards the sign-in page and the tour point at, the demo's decks, the Weekly numbers Workflow and the landing examples' periods), so the next visitor never finds a stranger's words on what the demo promises. A visitor may change the numbers, layouts and settings of what the seed made, not its names and descriptions.
- **A new table or server action fails a test until it is classified** (`demo_unclassified_tables()`, `demo-changes.ts`, the walk), so opening the demo never opens something by accident; a table nobody listed is refused, so the worst a forgotten line does is refuse a visitor.
- **A reset is a locked step** that waits for the writes in flight, and a visitor's write after it is refused as stale. It costs what the nightly seed cost, at most 96 times a day and only after a change; an operator measures it on a copy before opening the demo (`scripts/demo-reset-measure.mjs`, `scripts/demo-load.mjs`).
- **Switching it off is the way back**: the demo is read-only again from the next request, and the database's door closes at the next call of the reset job.
- **Changing any of this is a new ADR:** opening the demo on an Installation that holds real Workspaces, anything that sends or fetches from the demo, a demo whose changes outlast a reset, or a private copy per visitor.
