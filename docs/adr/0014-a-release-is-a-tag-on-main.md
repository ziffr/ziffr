# A release is a tag on main: the version comes from the tag, nothing is committed, nothing waits

A release is one conscious act of the owner and nothing else: the Release button (`.github/workflows/release.yml`, or `pnpm release`) tags the current commit of `main` as the next version `vX.Y.Z` and publishes it. Nothing is committed, no pull request is opened, no CI runs a second time and nothing waits for an approval. `main` takes no change without its required checks (`check`, `core-db`, `numbers`), so its newest commit is tested already; the button only refuses when `main`'s CI on that commit has not passed. The version is the tag's: the Docker image is built with it (`ZIFFR_VERSION`, shown on the Installation settings page), the npm packages are given it at publishing time, and the copies of `docker/compose.yml` and `docker/install.sh` the release attaches have it written in. No release changes the repository: the MIT packages' `package.json` say `0.0.0-dev`, the Docker files name a placeholder, and the product's `package.json` stay at 0.11.0, the last version committed, which the core uses only where no image gives `ZIFFR_VERSION` (development and tests). The release notes are the Changesets **added** to `.changeset/` since the previous tag (`git diff --diff-filter=A <tag>..HEAD`), with the bump levels in their front matter deciding the version as before (ADR 0004); they become the text of the GitHub release, grouped as the changelog sections were. The GitHub Releases page is the changelog from 0.12.0 on; `CHANGELOG.md` keeps the sections up to 0.11.0 as they are. The MIT packages (`@ziffr/sdk`, `@ziffr/mcp`, `@ziffr/feed-kit`, `@ziffr/feed-sql`) carry the product's version from 0.12.0 on and are published with every release. This supersedes the release mechanics of ADR 0004 and its two amendments of 2026-11-18; one product version, a release note with every change and semantic versioning stay.

## Considered Options

- **The release pull request** (ADR 0004's amendments): rejected; on a `main` that takes changes only through pull requests with passing checks, the bot's commit needed its own CI run, an approval for an unattributed change and a merge. 0.11.0 took hours and several presses for a commit that only moved text.
- **Committing the version after the tag** (a bot pushes the bumped `package.json` and the changelog to `main`): rejected; it needs an exception to `main`'s protection, which ADR 0004's first amendment refused, since the agents act with the owner's account.
- **Releasing on every merge** (continuous delivery): rejected; the owner decides when people get a version, and a release states the day it becomes AGPL-3.0.

## Consequences

- Changeset files stay in `.changeset/` after a release. Only files added after the previous tag count, so a stale file is never released twice; a normal pull request may delete old ones. A note edited after its release is not released again.
- A release cannot fix anything: what is on `main` is what is released. A fix is a pull request, then a new press.
- If a job fails after the tag is pushed, "Re-run failed jobs" finishes the release; the tag is never moved (the ruleset "release tags" forbids moving or deleting `v*` and `*-v*` tags).
- Publishing to npm is a job of the Release workflow, so only the owner's press publishes; it runs in the environment `release`, which npm's trusted publishing names together with `release.yml`. A required reviewer on that environment, if the owner keeps one, is the only wait left. The separate workflow that published on a package tag is gone.
- The agents act with the owner's account, so what keeps them from releasing is the rule in `AGENTS.md` (rule 12), as before.
