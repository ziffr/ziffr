# Threat model

What Ziffr protects, from whom, and how. Written in the security pass of spec 0001 (ticket #19); the API and the MCP server added with spec 0002. Keep it current: a change to who can see or do what updates this page in the same pull request. Issue numbers on this page (such as #19 or #42) refer to the earlier, private repository Ziffr was built in.

## What we protect

- **A workspace's numbers.** Metrics, their values, Breakdowns, targets and projections. For a business these can be revenue, cash and headcount; for a person, their finances or health.
- **Who said what.** Questions, tasks, Threads and Corrections, and who submitted which value.
- **People's details.** Names, email addresses, Slack handles and phone numbers of members and Contacts.
- **The right to act.** Sessions, Access Keys, Tokens (form links), Invitations and View Links.

## Who might attack

- **Someone outside any workspace:** anyone on the internet. They can reach the login page, the demo, View Links, form links and invitation pages.
- **A member of another workspace.** They are signed in, so every core function runs for them; they must get nothing of a workspace they are not in.
- **A member with a smaller role.** A Guest or Member trying to do what only Owners or Admins may do, or to see what was not shared with them.
- **Someone who left.** A removed member with an old session, link, Token or key.
- **A demo visitor.** Anyone may use the demo, which shares one workspace among all visitors. By default nothing a visitor does is saved: the database refuses every write to the demo's rows and its people's (migration `20261225110000_demo_read_only.sql`), and only its seed writes it (#271). On a demo-only Installation whose operator switched on `ZIFFR_DEMO_CHANGES`, a visitor may change the everyday work, in the one shared Workspace, within limits and until the next reset: see [The shared demo that visitors may change](#the-shared-demo-that-visitors-may-change-spec-0051-adr-0016).
- **A leaked secret.** A form link, View Link, invitation link or Access Key that reached the wrong person.
- **A program gone wrong.** A script or an AI assistant with a valid key that calls too often, retries blindly, or was steered by text it read.

## Trust boundaries

1. **Browser to server.** Everything a browser sends is untrusted: ids, text, settings, layouts, documents. Server actions are public endpoints, whatever page they are called from.
2. **App to core.** The web app's pages and server actions only call core functions (`packages/core`). Each takes the acting person (an `Actor`) or a key (`KeyActor`) first. The app has no permission code of its own.
3. **Core to database.** The core reaches the database with the service role. The web app holds it too, only to find the signed-in person and their membership (`apps/web/src/lib/auth.ts`, `viewer.ts`) and for the demo's "view as"; every page read and every change goes through the core (#42); it is never a `NEXT_PUBLIC_` variable, so Next.js never puts it in a browser bundle. Row Level Security is on for every table, with no policies, so the public key reads nothing.
4. **Programs to the API.** `/api/v1` accepts only an Access Key in the `Authorization` header, never a session or the demo cookie, and the middleware leaves it alone. The route handlers turn the key into a `KeyActor`, check the endpoint's scope, validate input with zod, and call only core functions written for keys. Anything the key's creator may not see answers 404. No CORS headers and no caching. Bodies are JSON of at most 64 KB; every query, path and body goes through the endpoint's zod schema, the same schemas the OpenAPI document at `/api/v1/openapi.json` is built from. That document is public: it describes what exists, never anyone's data (spec 0002).
5. **Feeds to the API (spec 0012).** A Feed is a program outside Ziffr that runs wherever its operator chooses, with a Feed Key. Ziffr never runs its code and never holds its credentials for the other system (ADR 0006). A Feed Key turns into a `FeedActor`, which has no person and no role, so no function written for people or their keys accepts it. It reaches only `GET /api/v1/feed` and `POST /api/v1/feed/observations`; every other endpoint answers 403. It sees only the Metrics its Feed is a Submitter of and whose API Source is on: their descriptions and which periods have a value, never a value, a person or a Group. Batches hold at most 500 items in at most 1 MB. The SQL Feed runs its queries in read-only transactions with bound period parameters and a time limit.
6. **Assistants to the MCP server.** `@ziffr/mcp` runs on the person's own computer over stdio, with the key from the assistant's settings. It is a client of the API like any script: each tool calls the API through `@ziffr/sdk`, it keeps no state, and it can reach nothing the key cannot. What it returns (Metric names, descriptions, values) is workspace content, which reaches the assistant's context. The same server is served at `/mcp` (spec 0023), Streamable HTTP and stateless, when `ZIFFR_REMOTE_MCP` allows it: each request needs a bearer credential (never the session or the demo cookie, never from the query string), builds the server anew, and its SDK client hands every call to the API's own route handlers in-process (`api-in-process.ts`, only the endpoints for people's keys), so the key check, scope, limit and Access Log apply to each tool. An `Origin` other than Ziffr's own is refused, no CORS header is sent, bodies are at most 256 KB (a larger Content-Length is refused before reading, and the stream is counted in bytes and cancelled once it passes the limit, `limited-body.ts`), and nothing is cached.
7. **Email (spec 0004).** The server now sends mail, but connects only to the SMTP server in `ZIFFR_SMTP_URL` of the settings in effect (the environment, else what an Installation Admin saved, boundary 14), never to an address taken from Workspace data. Messages are plain text with header values on one line (`mail.ts`), and go only to a member or Contact of the message's workspace at the address that workspace keeps, never in the demo; the retry job needs `ZIFFR_JOB_SECRET`. Replies come back through `POST /api/inbound/email`: only when signed (HMAC-SHA256 of timestamp and body with `ZIFFR_INBOUND_SECRET`, at most five minutes old, at most 1 MB), only for a known reply token (24 random bytes, one per sent email), only from the address that email went to (a From header proves nothing on its own: with `ZIFFR_INBOUND_AUTHSERV_ID`, a reply is taken at once only when the provider's own Authentication-Results say DMARC or DKIM passed for that domain; any other reply is held, changes nothing and is confirmed by a one-time link emailed to the address the Workspace keeps for the person, never the sender's: 32 random bytes, only their hash stored, the reply sealed with a key made from the token, single use, 48 hours, a POST to confirm, three waiting per email, the same answer for unknown, expired and used links, and refused if the address on file has changed since; the page shows the whole held text and any Correction's number, and a refusal or a provider's explicit DMARC failure emails nobody; Approvals are never taken by email unvouched; the link is only as private as the person's mailbox, so a shared or forwarded mailbox that gets the Prompt gets the link too, and proxies should not log paths under `/api/confirm-reply/`), within 30 days, once per Message-ID, never from an auto-reply, and at most 20 per email; they then take the same core paths as every other answer (`inbound-email.ts`). The reply token is the secret that answers as the recipient, so it never leaves the server: no loader hands it to a page. A workspace sends at most 500 emails a day, one inbox gets at most 20 an hour from all workspaces (counted by mailbox, so Contacts with `+tag` addresses or in other workspaces are the same inbox), and one person causes at most 300 a day from all their workspaces, each send claimed in the database under locks, so neither parallel sends nor new workspaces or Contacts make Ziffr a relay; an email over a limit waits without holding up others. A Prompt's personal form link is added only when it is emailed, never stored in the text the Outbox shows its sender; invitation emails have their own limits (50 a day per workspace and per person, three a day per inbox). Every Prompt and reminder carries a one-click unsubscribe link (RFC 8058) whose GET only asks, so link scanners stop nothing. See `docs/guides/email.md`.
8. **Schedulers to the jobs.** `/api/jobs/workflows` and `/api/jobs/deliveries` act for no person: they need `ZIFFR_JOB_SECRET` (at least 32 characters, compared in constant time), answer 404 without it and only counts with it. A day's Workflow run is claimed per workspace and local day in `workflow_runs` before anything is sent, so repeated or parallel calls never ask twice; it acts as one of the workspace's Owners, never in the demo. Owners and Admins may run today's steps by hand through the same claim; only the demo may pretend another day (spec 0005).
9. **Outside channels.** Values arriving by Slack, email or a form link are recognised by Token or by the sender's identity in one workspace. WhatsApp and tickets are simulated in the prototype.
10. **Slack (spec 0007).**
   - **The app's values** (client id, client secret, signing secret) are the environment's, or ones an Installation Admin saved on the Installation Settings page, the two secrets sealed there (boundary 14). No page or Connector gets them back.
   - **Connecting.** An Owner or Admin connects one Slack workspace with OAuth v2. The `state` is 24 random bytes, works once, for ten minutes, and only for the person and workspace that made it; the callback needs their session. Org-wide installs are refused, and one Slack workspace answers to one Ziffr workspace.
   - **The bot token** is sealed at rest with AES-256-GCM under the Workspace Key (boundary 22), with the Workspace, table and column as additional data; one connected before is opened with `ZIFFR_SECRETS_KEY` (`secrets.ts`) and sealed again by the re-encryption job or on its next use. Only the core's Slack code opens it (`slackBot`), and no loader returns it.
   - **Outgoing calls** go only to `https://slack.com/api` (or `ZIFFR_SLACK_API_URL`, https only), never to an address from data. Only Slack's error code is kept.
   - **Who gets messages.** A Slack Delivery goes only to a member or Contact of its workspace, to the Slack user found by their proven address (`users.lookupByEmail`) or linked with a code they sent the bot. A code has 80 random bits, lasts ten minutes and works once. Never by a stored handle, never to a deleted user, a bot or a user of another Slack workspace, never in the demo.
   - **What messages carry.** Workspace text is escaped, so it cannot become a link or a mention. The form link is added only when sending.
   - **Limits.** Sends are claimed in the database under locks: 500 a day per workspace, 20 an hour per recipient, 300 a day per sender, 40 a minute per Slack workspace. A 429 waits for its `Retry-After`.
   - **Incoming requests.** `POST /api/slack/events` and `/api/slack/interactions` take only bodies of at most 64 KB signed by Slack (`v0` HMAC-SHA256 with the signing secret, timestamp within five minutes, constant-time comparison). `url_verification` is answered only then, and is the one request a signing secret alone (before the client id and secret are set) lets through; it only notes for the Installation Settings page that Slack reached the address. Each event is claimed once by its `event_id`, and only events for a connected Slack workspace and the app's own id count.
   - **Replies** are taken only in the thread of a sent Delivery, from the Slack user its recipient is matched to now, within 30 days, at most 20 per Delivery. They take the core paths email replies take (`reply-routing.ts`). A button counts only on the very message it was sent on, pressed by that recipient.
   - **Approvals by Slack** are taken: Slack vouches for who wrote or pressed, unlike an email's From.
   - **Ending.** Uninstalling the app, a revoked token or an `invalid_auth` answer end the connection and forget who was matched. See `docs/guides/slack.md`.
   - **Connection notices.** A member is emailed, at the address they sign in with and never by the chat service itself, when a Telegram or Slack account becomes theirs (by a code, or a Slack match by address), and whoever a code takes an account from is emailed too, naming nobody. Account names are cleaned of anything that could be an address or link. A notice about a code carries a link signed for that one connection (Workspace, person, moment; HMAC under a key derived from `ZIFFR_SECRETS_KEY`, never from the job secret: without a secrets key no such link is made or accepted, and the email points to Connectors) that can only end it, and ending it is recorded in the Audit Log: it needs no sign-in, a GET only asks, it does nothing once the connection was replaced, and so it does not expire; a forwarded copy lets its holder disconnect, never connect or read more than the service and Workspace name. A match by address has no such link, since it would be found again; the email says how to replace it. A notice about an account the person has not been told about in the last day (known by a hash of the service's account id in the Delivery's reference) goes; repeats about one already announced stop at five an hour and twenty a day per person and Workspace; above twenty notices an hour or sixty a day of any kind, one summary an hour goes in their place, saying so. Failed Deliveries count for nothing. The numbers are read before each notice is made, so notices made at the same moment may pass them slightly. Proxies should not log paths under `/api/disconnect-chat/`.
11. **Telegram (spec 0016).**
   - **The bot token** is the environment's, or one an Installation Admin saved on the Installation Settings page, sealed there (boundary 14). It is never shown or logged, and no page or Connector gets it. It travels in every request path to `https://api.telegram.org` (or `ZIFFR_TELEGRAM_API_URL`, https only), so no request address and no Telegram error text is kept, only its numeric code.
   - **Per workspace.** Owners and Admins turn Telegram on; off by default and never in the demo. Off stops sending at once and refuses replies and button presses to what was sent before.
   - **Linking.** A bot cannot write first or look anyone up, so each person links their own account: a one-time code (32 random bytes, hash only, ten minutes, once) in a `t.me` link, sent back by Telegram as `/start` in a private chat. A member makes it signed in; on a personal form only a Contact can, never over an existing link, and a form cannot disconnect. One account is one person per workspace. A member's link moving to another account is told to the chat it was.
   - **A Contact confirms by email.** A form link opens without signing in, so a Contact's **Start** connects nothing: Ziffr emails the address the Workspace keeps for them a link of 32 random bytes together with the chat, the account's name (cleaned of anything that could be an address or link), a mark of that address and a mark of four random digits, keyed with the secrets key, so the link does not give the digits away. Only a hash of the whole token is kept, so no part can be changed. The bot tells the digits to the chat alone: they are not in the email or on the page. Confirming takes both, so a request started from another chat cannot be confirmed with the Contact's own number. Each number typed spends a try in one statement before it is compared (in constant time), and three wrong ones end the request. It works once, for 30 minutes, by a POST (a GET only says what confirming does), and not after a newer request, a `/stop` from the chat, a changed address, Telegram turned off, a connection made meanwhile or the Contact's removal; every refusal is the same page. A Contact gets at most three such emails an hour and five a day, counted under a lock. The Delivery has no sender, so no one else in the Workspace sees it in the Outbox. Without an address, working email, or in a trial, nothing can be started. Stopping Prompts by email does not hold this email back, since the person asks for it; the bot says whether it left. The Contact is told by email once connected. The link is only as private as the Contact's mailbox, and proxies should not log paths under `/api/confirm-telegram/`.
   - **Incoming updates.** `POST /api/telegram/updates` takes only requests with the secret derived from the token and `ZIFFR_SECRETS_KEY` (compared in constant time), at most 64 KB; each `update_id` is claimed once. Polling (`ZIFFR_TELEGRAM_POLLING`, for a laptop) runs only through a job with the job secret.
   - **Replies and buttons** count only as replies to (or presses on) a sent Delivery's own message, from the account its recipient linked, while that person still belongs to the workspace and Telegram is on there, within 30 days; at most twenty replies per Delivery and ten bot answers a minute per account. **Approve** is taken, as Telegram vouches for who pressed it; an Approval closes only while still open, in one statement, so two presses at once approve once (for every Connector). Someone who left the workspace gets nothing more, also nothing queued before. Updates and sends older than 31 days are deleted by the deliveries job.
   - **Messages** are plain text without a parse mode, so no workspace text becomes formatting or a hidden link. Sends are claimed under locks: 500 a day per workspace, 20 an hour per chat, 300 a day per sender, one a second per chat, 25 a second for the bot. See `docs/guides/telegram.md`.

12. **Strangers on hosted Ziffr (spec 0021, ADR 0010; spec 0040).** Only where `ZIFFR_CLOUD_KEY` is set and `ZIFFR_TRIAL_DAYS` gives the days (`trialsOffered()`; `createTrialWorkspace` refuses without the key too), anyone may sign in and make one Trial Workspace. Without the key there are no trials and no trial settings.
   - **Who is reached.** A Delivery in a trial is sent for real only to its Owner, checked when it is made and again in each Connector's send before its own settings; others stay in the Outbox. Invitations, invite links, domain joining and join requests are refused. Nothing is sent or taken once the trial has ended.
   - **Webhooks in a trial (spec 0037, #646).** A trial may add 2 Webhooks and send 200 a day (`webhook-trial.ts`, the one place that decides, for creating, testing and sending). `ZIFFR_WEBHOOK_PRIVATE_HOSTS` never applies to a trial, at save and at every send, so a trial reaches public addresses only, under the same outbound rules as any Workspace. `ZIFFR_TRIAL_WEBHOOKS=false` (or the page setting; the server's environment wins) refuses new ones and drops the sends of those that exist; an ended trial sends nothing. A trial is never turned into an ordinary Workspace by ending (there is no Free Size): only subscribing does, and then it is a paying Workspace's. The switch fails closed (settings that cannot be read count as off) and also stops a switched-off trial's inbound requests. The limit is counted under a lock of the Workspace and the daily cap is one atomic claim, so parallel requests cannot pass either.
   - **How much.** At most 50 real messages a day per trial over all Connectors, 25 Metrics, 2 Access Keys and 2 Feeds with 2 keys each, none working past its end, and `ZIFFR_TRIAL_MAX` live trials; all claimed in the database under locks or row locks. Ask me now asks at most once in ten minutes per Metric.
   - **Signing in.** Cloudflare Turnstile, checked on the server before a link is sent or a provider's sign-in starts, on top of the sign-in link limits. A trial setting that is set but wrong stops workspaces from being made. With Docker, the proxy lets only Auth's verify, authorize and callback paths through, so the check cannot be gone around. On a hosted Supabase project, Auth's own `/auth/v1/otp` is reachable with the public key and skips both: turn on Supabase's own captcha (Auth, Bot protection, Turnstile) with the same keys.
   - **The end.** Keys stop at the end; a week later the workspace, its Contacts' and Feeds' person rows, and its Owner with their sign-in are deleted.

13. **Files people bring in (spec 0024).** A View Design is a file from outside, pasted or uploaded, and may carry an Analysis Recipe. Nothing in either is ever run. The guides are [view-designs.md](../guides/view-designs.md) and [analysis-recipes.md](../guides/analysis-recipes.md).
   - **Checked on the server** whenever it is stored (`checkViewDesign`): at most 64 KiB and nested 10 deep, read by a parser that keeps lines and treats `__proto__` as data; then a JSON Schema with exact limits, unknown fields refused, every text plain (no `<`, `>`, braces, brackets, backslashes, line breaks, `://`, `www.`, `javascript:`, `data:`, `url(`). The browser's check is only a convenience.
   - **What it can show** is a fixed list of the core's results for the widget's own Metrics; it computes nothing, reaches no other Metric, and its colours are Theme tokens. The renderer draws its words as React text.
   - **Who adds one.** Only Owners and Admins add a design to the Workspace or remove it, never in the demo; both are audited. A widget on a dashboard or in the Pool draws only a design of its Workspace (the core puts the Workspace's stored copy in place of whatever the browser sent) or the copy it already had. Widgets on slides and in team templates keep their checked copy too. Every path a design can sit on in widget settings is checked, at any depth: the widget's own, the widget a Free layout starts from (`canvasSeed`, which only the server sets, from the stored widget; a browser can only clear it), and widgets on an artboard or a slide, as objects or as text (`widget-designs.ts`). Dashboard Templates and restored Versions are checked again as they become widgets; the API sets only a short list of plain settings.
   - **What a recipe can reach.** Its steps name only the library's functions (`recipe-functions.ts`, each in the Calculation Catalogue with a reference) and only `slot1` to `slot4` or earlier steps, never a Metric. `designRecipe` hands it the series the widget shows of the design's own Metrics, as the person sees them, and nothing else, so every number it gives is verified and none comes from outside the widget.
   - **What a file can cost.** A recipe works on at most the latest 120 values of each Slot, and every library function takes time in proportion to its series (whole numbers at one scale, a running sum for moving averages), so the heaviest recipe the checks allow runs in milliseconds; values that are not finite are left out. A check names at most 50 problems. A design that fails to draw shows a note in its widget only. Restored deck and template Versions are checked again too.

## Threats and how they are met

| Threat | Defence | Tested in |
| --- | --- | --- |
| Reading or changing another workspace's data | Every core function works in `actor.workspaceId`; every lookup by an id filters by workspace; rows that belong to another row take its workspace in the database (`workspace_from_parent`); visibility rules ignore rows of other workspaces | `*.db.test.ts` (each has an "another workspace" case), `visibility.test.ts` |
| Seeing what was not shared | Visibility is decided by the pure rules in `visibility.ts`; dashboards, decks, templates and restores check every Metric a widget draws, nested ones included (`widget-metrics.ts`) | `sharing.db.test.ts`, `dashboards.db.test.ts`, `decks.db.test.ts`, `widget-metrics.test.ts` |
| Doing more than one's role allows | Capabilities per Workspace Role (`actor.ts`); Guests create and share nothing; only Owners make or remove Owners; a database trigger keeps the last Owner | `invitations.db.test.ts`, `handover.db.test.ts`, `sharing.db.test.ts`, `fiscal-year.db.test.ts` |
| Taking over someone's identity | An address counts only when confirmed through a way of signing in that proves it (email link, Google); email confirmations are required; Contacts carry no address on their person, so nobody can sign in as one | `invitations.db.test.ts`; `provenEmail` in `apps/web/src/lib/auth.ts` |
| A leaked View Link | Unguessable token (24 random bytes); ends within 90 days; revocable; shows only the Metrics it was made with, only the dashboard widgets or deck records it was made with (links made before the security pass have no such list), people's names without contact details (with Show names on, only the owners of the shown Metrics, never a role, and older frozen copies and Snapshots are cut down the same way when served, ticket #902), and nothing to act on. A live link shows current values and current text inside the widgets and shapes it was made with, by design | `dashboards.db.test.ts`, `decks.db.test.ts`, `view-link-names.db.test.ts` |
| A leaked form link (Token) | Unguessable code; pages show a code only to its submitter, the Metric's owner and admins; records values only for its Metric and submitter; stops when the Contact is removed or the person leaves | `page-data.db.test.ts`, `submissions.db.test.ts`, `handover.db.test.ts` |
| A link that puts its own words on a Ziffr page (`?detail=` on a form link) | No page shows text from its address: the form link's result comes back from the server action into the form, and pages that take a code from the address (the Slack outcome on Connectors, a failed sign-in link) map it to fixed text | `submit/[code]/page.test.tsx` |
| A leaked Access Key | Stored as a hash; scoped; ends on a day within a year; revocable by its creator and by Owners; stops when its creator leaves; a `KeyActor` is a type of its own that no core function accepts unless written for keys, and it holds no role capability | `access-keys.db.test.ts` (including a compile-time check) |
| A stolen or replayed assistant connection (spec 0023, ADR 0011) | A connection is an Access Key of the kind `assistant`, so every row above holds for it. Its own secret is never shown and never works; it acts only through OAuth tokens of 256 random bits, stored as SHA-256 hashes. Codes work once for ten minutes, bound to client, redirect address, PKCE S256 challenge and resource; a code or refresh token presented twice ends the connection; refresh tokens rotate; access tokens last an hour and count only on the calls `/mcp` makes in-process, never sent to `/api/v1` directly; revocation by either token ends the whole connection | `assistant-connections.db.test.ts`, `apps/web/src/app/oauth/oauth.db.test.ts` |
| Abusing the public OAuth endpoints | Registration takes only a name (shown as untrusted text, control and direction characters removed) and at most five https or loopback redirect addresses; public clients only, no secret; 10 an hour per network address and 300 for the Installation, claimed under a lock; unused registrations forgotten after a day, never one a connection refers to, and tidying cannot block a registration. Redirect addresses match exactly (the loopback port aside, RFC 8252); a wrong client or address is shown an error and never redirected to. Form and JSON bodies at most 16 KB, read with a byte ceiling; a parameter sent twice is refused. Everything 404s while `ZIFFR_REMOTE_MCP` is off | `assistant-connections.db.test.ts`, `apps/web/src/app/oauth/oauth.db.test.ts`, `limited-body.test.ts` |
| Heads-ups reaching someone who may not see both Metrics of a pair, or confirming one exists (spec 0041, ticket 14) | A Heads-up is worked out per person over the Metrics they may see, so one about two Metrics exists only for people who see both, and nothing in it (sentence, count, order, correction) depends on any other Metric. A message is a new outbound channel naming Metrics: it is made only for a member who switched it on, sight of every Metric is asked again before the weekly claim and again in each Connector as it is sent (with the person's own mutes, Not useful and switch-off), at most 3 in 7 days, with a one-click stop link in the email; the Outbox shows it only while the person sees both Metrics; a reply is refused. Not useful, mutes and settings are the person's own rows, removed when they leave; Not useful and mute refuse a key or Metric the person does not see in the words of one that is not there. A person's own scan in a Workspace over the cap has a signature-matched cache, a per-person budget and its own lane for the job, so nobody is refused for another Workspace's load | `heads-up-delivery.db.test.ts`, `heads-up-budget.test.ts`, `heads-ups.db.test.ts` |
| Alerts reaching someone who may not see a Metric, or confirming one exists (spec 0032) | An Alert is the person's own, on a Metric they see; sight is asked when it fires, again before its message is queued, and again in each Connector as it is sent, so a message never leaves for a person who lost sight in between. An Alert that loses sight pauses silently and disappears from the list; its messages disappear from the Outbox and a held message keeps no reason. A message holds only its own Metric's name, period, value, target and link, never a Breakdown or another Metric, and the daily limit note names no Metric. Nothing said back is read: `routeReply` refuses the kind, email has no reply address, Slack and Telegram messages have no buttons. Limits (20 Alerts per person, 5 per Metric, 500 per Workspace, 20 messages per person and 2,000 per Workspace a day) are counted under an advisory lock. The stop link in an email is 192 random bits tied to one message, pauses only that Alert (or stops that Workflow's Tell), is idempotent and changes nothing on GET. The API and MCP need `alerts:write`, touch only the key creator's Alerts and validate every shape; the Starter quotes its arguments. Imports fire nothing; values not approved fire only for an Alert that asks. The table is sealed and RLS has no policies. | `alert-firing.db.test.ts`, `alerts.db.test.ts`, `api/v1/alerts/route.db.test.ts` |
| Tricking someone into connecting an assistant (the consent screen, spec 0023) | `/oauth/authorize` needs the person signed in (never in the demo) and shows the assistant's name only as its claim ("says it is"), as React text, with the host it returns to, and a warning when that is the person's own computer, where any program can claim any name. Only reading is ticked at first, whatever the assistant asked for; the Workspace must be one of theirs, and scopes and end date are checked as for any Access Key. The answer is a server action (same origin only) that checks the request again from its parameters, never from what the page held; parameters given twice are left out. Errors are shown on the page and never redirected, so it is no open redirect; the browser leaves for the assistant only on Connect or Cancel. The page cannot be framed (`frame-ancestors 'none'`). 60 consent screens an hour per network address. 14. **Running the Installation from a page (spec 0025).** `/installation` and its server actions are a new way to change what the whole Installation does.
   - **Who.** Installation Admin is a role of its own (`installation_admins`), not a Workspace Role: no Owner, Admin, Access Key, Feed Key or demo visitor is one. The page and every action take the person behind the session (`lib/installation.ts`, never the demo's "view as"), and the core checks the role on each call; anyone else gets "not found". `ZIFFR_INSTALLATION_ADMINS` names admins by address, matched only against an address a sign-in proved.
   - **Claiming.** While there is no Installation Admin, Ziffr writes a setup code (80 random bits) to the server log at start and when the claim page opens with none waiting; only its SHA-256 hash is stored. Holding the log proves you run the server, which signing up first does not on an Installation with trials. The claim runs in one database function under a lock: once only, never while an admin exists or the server names admins, and the code is deleted on use. Wrong codes count per person (five an hour), so nobody can use up the code the operator is about to type. Only people with a sign-in can claim or be added; never a Contact or a demo person.
   - **Adding and removing.** By the address of a person who has signed in before; the answer is the same for "nobody" and "a Contact". The last admin cannot be removed, and the database checks under the same lock that the one removing still is an admin, so two removing each other leave one. The setup code is made in one step with the check that nobody runs the Installation. The last admin's person row cannot be deleted (a trigger refuses it), since that would leave the Installation open to a new setup code; a trial's cleanup then keeps that one person.
   - **Settings.** One row per setting in `installation_settings`, which only the service role reaches; only names the page knows are read from it, so the table cannot set `ZIFFR_JOB_SECRET` or any other environment variable. Secrets are sealed with AES-256-GCM under `ZIFFR_SECRETS_KEY`, bound to their name, and never returned: the page gets "set" and at most the last four characters. Values are checked on the server: an SMTP URL must be `smtp:` or `smtps:`, without a query, and its host must be global unicast (CIDR lists in `mail-hosts.ts`: no loopback, RFC 1918, CGNAT, link-local, 0/8, benchmark, documentation, reserved, multicast or broadcast range, nothing outside 2000::/3, no ULA, Teredo or documentation IPv6, and IPv4 inside IPv6, whether mapped, translated, compatible, NAT64 or 6to4, judged by the IPv4 it carries; no bare name such as `mail`) unless the server sets `ZIFFR_ALLOW_PRIVATE_MAIL_HOST=1`. That is judged on the name as written and on every address it resolves to, on save and again at every send; the send then connects to the address it checked, with TLS checking the certificate against the name, so DNS rebinding reaches nothing new (`mail-hosts.ts`). Only the address `ZIFFR_SMTP_URL` (or Docker's `ZIFFR_SMTP_URL_DEFAULT`) sets is used unchecked; every other one is checked, so a failed read of the settings cannot skip the check. The environment always wins.
   - **The mail connection** is built from the address's host, port, TLS (`smtps:`) and decoded login only (`smtpOptions`), whether the address comes from the page or the environment, so nothing in a stored string (`?logger=`, `?proxy=`, `?tls.rejectUnauthorized=`) becomes a nodemailer option.
   - **What an Installation Admin can do.** Point the Installation's mail at any public SMTP server, which receives every email Ziffr sends; that is the trust of running the server, so an Installation Admin is someone you would give the server's settings file. The test email goes only to the admin's own proven address, at most ten an hour per admin (counted and recorded in the Installation's audit in one locked database step, `claim_installation_test_email`; any error there refuses), and a failure answers one of four fixed messages, never the server's code or words, so it is no port scanner. A failed Delivery shows Workspace members the mail server's error code only, and the Installation's own host checks (`EPRIVATEHOST`, `EDNS`) as a plain "error".
   - **Telegram (#199).** A bot token saved on the page is checked with Telegram (getMe) before it is stored, so a wrong one never replaces a working one, and only the name of the bot it belongs to reaches the page. The webhook is then registered with the secret derived from the token and `ZIFFR_SECRETS_KEY`, as before. Replacing or removing it tells the old bot to stop sending here (deleteWebhook); if that fails, the old bot's updates carry a secret Ziffr no longer accepts and get 404. Calls go only to `api.telegram.org` or `ZIFFR_TELEGRAM_API_URL`, never to an address from the page. **Check Telegram** shows Telegram's last error about reaching the webhook, which names this Ziffr's address at most.
   - **Slack (#200).** The client id, client secret and signing secret are checked for their shape only: Slack offers no test of the client id and secret before a Slack workspace is connected. The page's one test is Slack's signed `url_verification`: when one arrives signed with the signing secret in effect, `installation_checks` keeps the time and a SHA-256 fingerprint of that secret (never the secret), so a check made with a secret since replaced stops counting. The **Create the Slack app** link carries the manifest for `ZIFFR_SITE_URL` only when that is https with nothing after the host, so no other address goes into it.
   - **Telegram's round trip test.** **Test Telegram** makes a one-time code (32 random bytes, prefix `zt_`, SHA-256 hash only, ten minutes, used once in one statement) for the Installation Admin who asked, checked again to still be one on Start. Its shape is one no Workspace connect code has, and it lives in a table of its own (`installation_telegram_tests`, service role only): a test never links an account, makes a Delivery or touches anyone's Delivery Preferences, and a connect code is never taken as a test. The chat id is kept only while the test waits for its answer (cleared on the answer, on a failed send, and once ten minutes pass). Only a reply from the account that pressed Start, to the test message, finishes it. Five tests an hour per admin, counted and recorded under a lock; the bot's own answer limits apply.
   - **Sign-in emails (#198).** Supabase Auth hands each sign-in email to `POST /api/auth/send-email` (its Send Email Hook), so Ziffr sends it through the mail server in effect. The route is open in the middleware and its signature is the whole defence: a forged call would send sign-in emails to anyone. It answers 404 without `ZIFFR_AUTH_HOOK_SECRET`; otherwise it takes only a call signed with it (Standard Webhooks: HMAC-SHA256 of id, timestamp and body, compared in constant time, within five minutes, at most 64 KB read as a stream, each call id taken once; several secrets while one replaces another), and sends nothing else. In Docker, Caddy answers 404 for the route from outside. The link goes to Supabase Auth's own verify address with the token hash Auth gave, and `redirect_to` must be `ZIFFR_SITE_URL` or below it, so the hook is no open redirect; only the five kinds Auth sends for Ziffr are taken, in Ziffr's words, and errors give Auth a fixed code, never the mail server's words. Docker makes the secret on the first start and has Auth call the app at `http://host.docker.internal:3000` on a network only Auth and the app share (`authhook`, internal), since Auth takes plain http only for that name: the call never leaves the stack. Ziffr's own sign-in link limits run before Auth is asked (`claimSignInLink`).
   - **Replies by email (#198).** The page makes the inbound signing secret (32 random bytes) and shows it once, to copy into the provider's forwarder; it is sealed like any secret and never shown again, and making a new one ends the old one at once. The replies test emails the admin's own proven address with a reply address of its own (24 random bytes, SHA-256 hash only, thirty minutes, used once in one statement, ended by the next test), at most five an hour per admin. A reply to it comes in through the same signed route and limits as any reply, reaches no Workspace, Thread or value (`installation_reply_tests`, service role only), and keeps only its time, whether it came from the admin's address and whether the provider vouched for it, never its text. The MX lookup reads only the replies domain in effect, with a time limit.
   - **Bots, trials and the demo (#201).** A Turnstile secret key is asked of Cloudflare before it is stored (a siteverify call with an answer no widget gave tells a known secret from an unknown one), so a wrong one never shuts out every sign-in, and is sealed like any secret. The sign-in action reads both keys from the settings in effect, so a check saved on the page is enforced at once. Trials and whether the demo is offered are read from the settings in effect everywhere (`trialSettingsInEffect`, `demoEnabled`); `ZIFFR_DEMO_ONLY` stays the server's, since it also stops Auth from making accounts. The middleware cannot read the database: it honours `ZIFFR_DEMO=0` from the environment (which wins over the page) and otherwise passes the demo's cookie, and every page and action asks `isDemo()`, which reads the setting in effect, so a demo the page turned off counts as no visit. That is a known weakening against a demo off in the environment: there the middleware itself keeps a forged demo cookie from passing sign-in. Docker therefore writes `ZIFFR_DEMO=0` into the environment on a domain unless the settings file says otherwise, so a company Installation keeps that gate; the page can switch the demo off only where it was on. A Turnstile secret saved on the page that no longer opens closes the sign-in until saved again, rather than switching the check off.
   - **Audit.** Claiming, adding, removing, saving, removing a setting and test emails are recorded in `installation_audit_events` (add-only by trigger, the database's time) with the setting's name, never its value.

15. **Ziffr Cloud to the Cloud API (spec 0029, ADR 0013).** Hosted Ziffr's billing service sets each Workspace's limit on Metrics through `/api/cloud/v1` (`cloud-api.ts`, `lib/cloud-route.ts`).
   - **The secret.** `ZIFFR_CLOUD_KEY` (at least 32 bytes) lives only in the server's environment, never on the Installation Settings page. Without it every endpoint answers a bare 404 and no handover button shows. Two keys are derived from it with HKDF-SHA256 and labels of their own (`ziffr/cloud-api/v1`, `ziffr/cloud-handover/v1`), so a handover token can never sign a call.
   - **Signed calls, not a bearer key.** Each call carries `Ziffr-Cloud-Signature: t=<unix time>, v1=<hex HMAC-SHA256>` over the time, the method, the path with its query and the SHA-256 of the body. It is compared in constant time, refused when more than five minutes old or ahead, and claimed once in `cloud_api_calls` (kept fifteen minutes), so a replay is refused; at most 60 calls a minute pass. Bodies are at most 4 KB, checked with strict zod schemas (unknown fields refused, labels plain text of at most 30 characters, limits 1 to 1,000,000). No session or cookie counts, no CORS header is sent, nothing is cached. It is not an Access Key: it never reaches `/api/v1`, `/mcp` or a person's data.
   - **What it reads and sets.** A Workspace's existence, Metric count, limit, label, room, `over_limit_since`, trial end and who set the limit; never a name, Metric, value or person (a test lists the keys). It sets a limit, its label and a coming change, or gives the Workspace back to the default. It cannot make, delete or change anything else; values keep arriving whatever it sets. Each write is in the Workspace's Audit Log and the Installation's audit as "Ziffr Cloud".
   - **The handover.** **Change Size** and **Billing and invoices** post to `/settings/size/handover` from Ziffr's own pages (the Origin is checked). The core checks the person is an Owner of the Workspace in the database, signed in with a proven address, never with a key and never in the demo, and signs a token of the Workspace's id and name, the person's id and address, the role, the purpose, a random nonce and an expiry five minutes ahead. A page posts it to `ZIFFR_CLOUD_URL` (https) in a form, so it never sits in a browser history, a server log or a Referer (`no-referrer`). Ziffr Cloud takes each nonce once. Ziffr trusts nothing Ziffr Cloud puts in the address it sends the Owner back to.
   - **A leaked key** can set any Workspace's limit, so it can stop new Metrics in it, and read Metric counts. With `endTrial` it can turn a Trial Workspace into an ordinary one (which can then invite people, ADR 0010), and with `metrics: null` it can give a paid Workspace back to the default limit, which makes it eligible for deletion as unused after the usual days and a warning email. It cannot read data, make or delete anything, or stop values arriving. Rotating `ZIFFR_CLOUD_KEY` on both sides ends it.
16. **Deleting unused Workspaces (spec 0029).** Off unless `ZIFFR_DELETE_UNUSED_AFTER_DAYS` (30 to 3650; a wrong value counts as off), a default Workspace Limit and working email are set. The daily job needs the job secret. Only a Workspace on the default limit (no limit of its own), never a trial or the demo, unused (no sign-in or page of a signed-in person, no new or changed value by any Source) for the days set, is warned, once, by email to its Owners (`claim_unused_warning`; a warning that reaches no Owner is taken back). Fourteen to 21 days later (an older warning is stale and starts again; a limit of its own clears it) the database checks it all again under the Workspace's row lock and, unused for the days set before the warning and since, and only after the warning's email was really sent, destroys its key and deletes it in one step (`delete_unused_workspace`), so a key is never destroyed for a Workspace that stays; any use clears the warning. Members whose only Workspace it was are deleted with their sign-in, as with trials, never an Installation Admin. The Installation's audit keeps its id, never its name. The values download the warning offers holds only the Metrics the Owner or Admin sees.

16. **Packs, files from outside (spec 0030, ADR 0013).** A Pack is one file of Metric Catalog entries, Dashboard, Deck and Workflow Templates, View Designs, Analysis Recipes and Themes, uploaded by an Owner or Admin or fetched from the Marketplace (boundary 17). Nothing in it is ever run. The guide is [packs.md](../guides/packs.md); the format and its checks are the MIT package `@ziffr/pack`, which the core uses, so the server and `npx @ziffr/pack check` run the same code.
   - **Checked in full on the server** before anything is shown or written (`checkPack`): at most 1 MiB and nested 20 deep, read by a parser that keeps lines, refuses a field given twice and treats `__proto__` as data; at most 200 items, 50 of a kind, each within its own format's size; unknown fields refused; every text plain (no markup, braces outside the known Placeholders, line breaks, or anything that reads as a web address, `evil.com` or `https:x` included; the text check reads Unicode the way a person does, so an address is also looked for with compatibility forms as plain characters and without combining marks and characters that show nothing); web addresses only in `listing`, https only, shown as plain links that name their site when the Marketplace did not check the Pack. Each item passes its own format's checks, View Designs and recipes exactly as when pasted, and names only items of the same Pack. A Theme holds no image or font file; the one image a Pack may bring is its logo (below). A check of a near-1 MiB Pack takes well under a second (`pack.test.ts`).
   - **`ziffr.pack/2` (spec 0058)** adds Positions, Repeats, credit and a Pack Guide, held to each other by the same package (`pack-2.test.ts`). A Position is a key in a file and grants nothing. An install keeps which items and steps name which Position (`places` in its manifest, read back defensively; no Workflow Template stores one), and leaves credit out. It keeps the guide, which `installed-pack-guides.ts` gives only to those who see the installed Packs (a person of that Workspace who is not a Guest, never an Access Key), checked again as it is read, and never to a Snapshot, a View Link, a message or the Workspace Export. The texts of **Describe your Pack** are untrusted too: the core reads only five texts of bounded length, makes the blocks and holds them to the format's own checks (`pack-guide-text.ts`); the list they start with is made from the very Pack the export would write (`pack-export-guide.ts`). A Total names one entry of a Repeat and where its target comes from, nothing about who sees it: no field of a Pack opens a Total. Until Totals are built (#1226), a Pack holding one is refused whole at installing and updating (`notBuiltYet`), so its entry never becomes a Metric that takes values. The Pack Guide is a stranger's text: fixed blocks, never Markdown or HTML, every text plain also as it reads without its bold marks (so marks cannot hide an address or words aimed at assistants), at most 32,768 bytes. Credit is what the file says and proves nothing. `comesFrom` (the kind of system and a note) is a stranger's text of the same kind: plain, bounded, read by the assistant-words check, drawn only through `PackNumbersView`; the overview an install keeps is held to its own schema when read, and at Set up the Pack's word only ever asks fewer people, never more. A page draws a guide only through `PackGuideView` (`apps/web`): each text a text node, bold runs from `guideRuns`, under section titles Ziffr writes, never Markdown, HTML or a link, with the words "written by" and the author the file names.
   - **The logo (spec 0039)** is the one image a Pack may bring: a manifest field beside `listing`, never in `contents`, at most 128,000 bytes as Ziffr writes it out and 512 pixels on each side (`@ziffr/pack/logo`, the same code that checks a Theme's logo). A PNG or JPEG is only measured from its header, never parsed for text; the bytes must be the type they say; WebP is refused. An SVG is read by a strict parser for the small part of XML a logo needs (no DOCTYPE, entity other than the five predefined, CDATA, processing instruction or non-ASCII name), held to allowlists of elements, attributes and namespaces (no script, handler, `style`, `use`, `image`, `a`, animation or foreign content; `href` only to `#…`; no `url()` outside the picture, `data:`, escapes or unknown functions), limited in depth, elements and attributes, and written out again from the tree, so only what was checked is ever kept or served. It is drawn only in an `img` in a bordered box on the Packs page, the install preview, the update and uninstall pages and the Marketplace, never inline and never in Ziffr's own chrome. An installed Pack's logo is served from `/api/packs/<install>/logo/<keyed hash>` to signed-in people of that Workspace only (never Guests or keys), checked again on every request, with `nosniff` and a `sandbox` Content-Security-Policy; uninstalling ends it. A Theme that says `"logo": "pack"` gets a copy; installing never makes it the team default, and making it the default (which puts the logo on emails, forms, View Link pages and Slack) asks first, naming whose logo it is. On an uploaded file the logo and author are self-declared and the page says so; only the Marketplace proves a handle. Impersonation by a lookalike logo is an accepted risk on the Marketplace: a person reviews a creator's first Pack and every later version that changes the logo or author, and a Pack with someone else's mark is taken down (the creators' guide says the logo stays the publisher's).
   - **Texts aimed at assistants** (`assistant-words.ts`) are listed with their place before installing or updating and need a tick: descriptions reach assistants through the MCP Server. A filter for the obvious, not a protection (accepted risk "Assistants read workspace text").
   - **Who.** Owners and Admins install, update and uninstall, an Owner when Themes are involved; never a key, never in the demo, where reading or fetching a Pack is refused before any work. Members see which Packs are installed and what each added; Guests see none. An uploaded file installs only after its uploader confirms the Marketplace did not check it.
   - **What installing does.** One database step (`install_pack`, security definer, run only by the service role, a lock per Workspace) copies each item into the table it lives in, marked with its install, key and hash. It makes no Metric, Workflow, dashboard or deck, sends nothing and changes nothing already there. A Workspace holds at most 25 Packs, 1,000 catalog entries from them, 1,000 templates and 100 View Designs. Catalog entries are the Workspace's own part of the Metric Catalog; no other Workspace lists or names them (`metricCatalog`, `createMetric`).
   - **Updating and uninstalling** (`update_pack`, `uninstall_pack`) touch only rows of that install in that Workspace, never what was made from a Pack; a copy the Workspace changed is kept, its new version only offered, and a step stops when a template or Theme changed after it was worked out. Taking an offered version of a template is for its installer or an Owner.
   - **Set up from this Pack** makes Metrics, dashboards and Workflows through `createMetric` and the other core functions, so the Workspace Limit, permissions and the Audit Log apply as for anything made by hand.
   - **A Pack that proposes who does what (spec 0058)** is a stranger's file asking for people's names to be put into places. Only the person setting up names people, each checked against the Workspace and against what each place allows (a Contact is never shared with or made Approver, a Guest never stands in), and no Workspace Role changes. The plan before it (`planPackSetup`) writes nothing, answers who will see what with the app's own visibility rules over the rows as they would be, and names only Metrics it would make and Metrics the actor sees. A proposed Share is made only when its id was ticked; the form ticks by itself only a Viewer who sees no more through it. Nobody but the person setting up is asked for a value at once unless that was ticked. Approvers, Stand-ins and people told see what those places already show, which the plan says. A large Set up works in steps: lines are checked on the server (plain text, a name each, at most 50 a Repeat and 200 Metrics), the whole set is held to the Workspace Limit before the first step, and a further step is taken only by the person who started it, with the same choices (a digest kept in the record), once. **Adding a line** reads the record only to know where to look: a Metric computed from one made before needs the actor to own or edit it, the shared Workflow is joined only when the actor owns it, a widget changed only on a dashboard they may edit, each only when ticked and through the core operation used by hand, with who then sees the new Metrics listed first.
   - **The record of a Set up** (`pack_setups` and its lines, people and items) decides nothing: no permission, message or sight is worked out from it. Only the core reads and writes it (no browser grant), line names are sealed with the Workspace Key, removing a person takes them out of it, uninstalling deletes it, a Workspace Export leaves it out and says so, and the Audit Log's `pack.set_up` holds counts, never names. The demo's tables list closes it.
   - **Export as Pack** (`pack-export.ts`) gives out only Metric Descriptions of Metrics the person sees, never a value, owner, Submitter, Token or id, and only words that pass the plain-text rules; background images never go out, and of logos only the one the person picks as the Pack's, checked like any Pack logo, with the Themes that show it saying `"logo": "pack"`. The file is checked as a Pack before it is handed over.
17. **Ziffr to the Marketplace (spec 0030).** An outgoing connection, off unless an Installation Admin or the server turns it on (`ZIFFR_MARKETPLACE`), to `ZIFFR_MARKETPLACE_URL` (`marketplace.ts`).
   - **Where.** Only from the server; https only, no user, query or fragment; never inside the server's own network unless `ZIFFR_ALLOW_PRIVATE_MARKETPLACE=1`, judged on the address as written and on every address its name resolves to, and the connection goes only to those, a new one each time. No redirect is followed; every answer has a size cap and the whole request ends within 10 seconds, also when it trickles in.
   - **What is sent.** A search (at most 100 characters), a Pack's id and version, and once a day for the whole Installation the Packs installed from the Marketplace with their oldest version, and Ziffr's version. Never a Workspace's name, id or data, nor a person (`marketplace.db.test.ts` records every request). On an Installation with one Workspace, that list is that Workspace's Packs from the Marketplace; the setting's text says what is sent.
   - **What is taken.** Listings field by field, free Packs only; a file only with a Signed Statement about it (spec 0059): a valid Ed25519 signature over the statement's exact bytes by a key in `MARKETPLACE_PUBLIC_KEYS` or the server's `ZIFFR_MARKETPLACE_PUBLIC_KEY` (never a page's), naming that key, the Pack and version asked for and the file's SHA-256; and then every check of an upload. The statement is read only after its signature held, and a field given twice or unknown refuses it. The signature tells where a file came from; the checks are the protection. `MARKETPLACE_PUBLIC_KEYS` is empty until Ziffr's Marketplace signs.
   - **Revocations.** Keys have a part. Only a reserve key's signature takes a signing key out of use; one by any other key, or naming a reserve key, is ignored, so a thief of the signing key cannot revoke anything. A revocation travels in the version and updates answers, counts for the answer it comes with, is kept for the whole Installation (`marketplace_revoked_keys`, no browser role) and is never removed; if it cannot be read, no file is taken. A reserve key signs statements only once it has revoked a key. What remains (spec 0059): whoever holds the signing key and also answers at the Marketplace's address can hide a revocation from an Installation that never saw it, until a release removes the key.
   - **The reserve key stays offline.** Its private key is on no machine the Marketplace or its signer runs on and in no account that can reach the signing key; whoever holds it can revoke the signing key and sign in its place, and no key can revoke it. It is used once, in an incident. **A release replaces it**: it removes the revoked key from `MARKETPLACE_PUBLIC_KEYS`, lists the former reserve key as the signing key and ships the public half of a new reserve key, made and kept offline. Until that release ships, the promoted key cannot be revoked. A self-hoster does the same in `ZIFFR_MARKETPLACE_PUBLIC_KEY` ([the steps](../guides/self-hosting.md#a-marketplace-key-of-your-own)). A key set in both parts is warned about at server start (`marketplaceKeyProblem`).
   - **Withdrawals** (spec 0059) travel in the updates answer: kept only for Packs that were asked about, with a reason held to the contract (plain text of at most 200 characters, no web address or markup) and shown as text (`marketplace_withdrawals`, no browser role). They change nothing in a Workspace: installed copies stay. An answer without the field changes nothing; one with it replaces what was kept for the asked Packs, so whoever answers at the address can also take a withdrawal back or claim one, which costs a line on a page and the offer of updates.
   - **Browsing and reporting.** The newest Packs are asked with an empty search when an Owner or Admin opens the Packs page; nothing about the Installation is sent besides what is listed above. A listing's words are shown as text. **Report this Pack** is a link the person's browser opens, built by the core from the checked Marketplace address, id and version, with no referrer and no opener; the server sends nothing.
18. **Requests to addresses people name (spec 0034; first the Marketplace, then Webhooks).** One shared piece, `outbound-request.ts`, makes every such request, so the Marketplace and Webhooks have the same rules.
   - **SSRF.** https only, no user or password. The name is looked up for every request and every address it has must be public (private, shared, loopback, link-local, cloud metadata, multicast, documentation, and IPv6 forms that carry IPv4: mapped, translated, compatible, NAT64, 6to4); an address written as an IP is judged the same way. One private answer among public ones refuses the request.
   - **DNS rebinding.** The connection goes only to an address that was just checked, on a connection of its own, so a name that changes its answer afterwards reaches nothing new; TLS checks the name.
   - **Redirect, slow, large.** No redirect is followed. The whole request ends within 10 seconds however slowly it trickles in; the answer is read to a size cap and then dropped (`outbound-request.test.ts`, against a real local TLS server).
   - **The operator's list.** `ZIFFR_WEBHOOK_PRIVATE_HOSTS` (comma-separated exact host names, no ranges or wildcards) lets those hosts, and only those, reach the server's own network, for a self-hoster's n8n. It is read from the server's process settings only, never from Installation Settings or anything a Workspace can write, so a Workspace Admin cannot widen it; a subdomain or a longer name never matches, and https stays required.
19. **A Webhook's status back (spec 0034, ticket #402).** `POST /api/webhooks/{id}/in` is open in the middleware and its signature is the whole defence.
   - **Judged from outside, in order.** A well-formed id, the Webhook on, a timestamp within five minutes, the HMAC-SHA256 of `<timestamp>.<raw body>` equal to one of its secrets (the new one, and the old for 24 hours after a replacement; constant time), then the request claimed once per Webhook by a hash of its timestamp and body (what the signature covers, so a replay changes nothing whatever a header carries; a retry is signed again); a signature header with anything but one or two well-formed `sha256=<hex>` entries is refused within 60 requests a minute. Everything before the claim answers the same 404, so nothing says whether an id exists; 429 only for a caller that proved the secret. The body is read as a stream to 16 KB (413 beyond), as the text the signature was taken over, and only then as JSON, field by field with fixed lengths; nothing in an answer repeats what was sent (`webhook-inbound.db.test.ts`, `route.db.test.ts`).
   - **What a leaked secret can do.** Only `link`, `done`, `reply`, `answer` and `reopen`, only on Actions that were sent to that Webhook (a delivered or in-flight send, or one it linked itself), whose Metric the assignee still sees, as the assignee "via" the Webhook, in the Thread and in the Audit Log ("by Webhook ..."). It reads nothing but `changed` and `status`; it cannot create or reassign anything, reopen a Question or a Task Ziffr closed itself, record a value or touch an Approval or a Self-check (whose own words a Webhook never speaks); its text is plain, never a Correction, a value or a command, escaped where shown. The fix is switching the Webhook off and replacing the secret (a replaced secret still signs for 24 hours so the receiver can switch without a gap; switching off ends that at once). At most 10 things a Webhook adds to one Action's Thread in an hour, and it never writes into a closed Action.
   - **A Personal Webhook's status back (spec 0037, ticket #643).** The same address and checks, acting as its person (`WebhookActor.owner`, not an Actor): after the signature, the Workspace's switch and the person's role are judged again (an off switch answers the same 404), and each request re-checks with `personalWebhookMayHear` that the person still sees the Action as the app shows it to them; one that is not theirs, was never sent to this Webhook or is no longer visible answers like an unknown one. Done, reopen and answer only for the person's own Actions as assignee; a reply also for one they asked. Words are plain and never a command, so no approval; the Thread, the hourly limit and the Audit Log go by the Webhook's name with its person's ("To Do (Ann's Webhook 3fa9)"), so it cannot pass for or block a Workspace Webhook (`webhook-inbound.db.test.ts`).
   - **One truth.** Each change goes through `changeActionState` (or the reply the app uses) with the Webhook as its origin: one event to every other Webhook, marked with the reporting one's id, and none back to the reporting one (no echo), and a repeat answers `changed: false`. External ids and their addresses are sealed with the Workspace Key; an event carries back only the ones its own Webhook made; one Action has at most 10 over all its Webhooks. The task-list Automation Templates take only the Tasks of the person named in their `assigneeEmail` setting, since a Webhook is sent every Action of the Workspace. Known and open: unsigned requests to the route cost a database read and a key opening before any limit (#487).
20. **What is looked at (spec 0031).** Ziffr counts opens and reports them; it never records who looked. Guide: [usage.md](../guides/usage.md).
   - **View Counts hold no person.** A row is a Workspace, a day, a kind (dashboard, deck, Metric), an id, a way in (signed in or View Link) and a number: no person, session, address or cookie. `recordView` takes only the Workspace; the demo and revoked or expired View Links are never counted; the middleware strips a client-sent `x-ziffr-no-count`. The Usage page and the digest list what was not opened and the most opened items of the last 30 days, only of dashboards, decks and Metrics the reader may see.
   - **Who reads the lists.** Owners and Admins of that Workspace, never a key, never in the demo. Archiving the Metrics it suggests takes each id through the same visibility and role check as archiving one, up to 200 at a time, and undoes the lot if one fails.
   - **The Usage Key** opens `GET /api/v1/installation/usage` and nothing else: it has no Workspace, is not an Access Key or a session, and the job secret does not open the address. 32 random bytes, only its SHA-256 stored, compared in constant time, shown once, one live at a time (making a new one revokes the old), 60 calls an hour, made and revoked by Installation Admins only and audited without the secret.
   - **The endpoint returns counts.** A fixed list of figures, whole numbers, never the name of a Workspace, Metric or person. Breakdowns (kinds of Workspace, Sources, Packs) are left out when fewer than 3 Workspaces are behind them, the three kinds only together, and an Installation with fewer than 3 Workspaces gets totals only. The Workspace left out of the figures must be one the Installation Admin owns, because leaving one out changes the next day's totals by exactly that Workspace; it is never named, and each change is in the Installation's audit.
   - **The Usage Feed** (`packages/feed-usage`) is off until both keys are set. The app never reads its keys; `init.mjs` writes them only into the clock's settings, the clock removes the job secret before starting it, and it refuses redirects when it reads the Usage Key's address. Its addresses are the operator's own settings.
   - **A Workspace's own figures (ticket #370)** are `GET /api/v1/usage`, for a program's Access Key with the scope `usage:read` only: the scope is not offered to assistants, refused in the core and by a check in the database (`access_keys_assistant_never_approves`), and not reachable from the MCP Server's in-process calls. It is checked again on every call: a live program key, its creator still an Owner or Admin, not the demo. It reads only the key's own Workspace, reuses the Usage page's loaders and returns whole numbers under a fixed list of keys (a test fails on any other key or on a name, id or person in the answer). Only what the creator sees is counted (values for the Metrics they see, views of the dashboards, decks and Metrics they see), since the Feed that records the figures writes Metrics others may see. Event figures and the Submitters wait for 3 people and start on the day the third joined (a day's total less one's own activity is another person's); what is not opened waits for 90 days of counting; 30 calls an hour per Workspace; the Feed that sends them is an ordinary Feed.
   - **The monthly digest** goes only to Owners of Workspaces that are neither the demo nor a trial, built from what that Owner may see, with names cleaned for headers and mail. Its unsubscribe link is an HMAC of the person's id under a key derived from the server's secret (constant-time compare, shape-checked): GET only shows a page, POST opts out. It does not expire, because the opt-out covers all the person's Workspaces and does nothing but stop mail.


21. **Retention (spec 0033).** The one thing in Ziffr that deletes values on purpose, so every path to it is narrow.
   - **Who may set it.** A Metric's Retention: its Metric Owner, an Owner or an Admin, never a Guest, an Access Key or an assistant (the API and the MCP Server only read it, and show the setting, never who set it or the counts). The Workspace default: Owners only. A Derived Metric has none, and the demo cannot set one. A person who may not see a Metric cannot preview it, and the preview names a Snapshot or a deck only to someone who sees it and every Metric in it (`retention-setting.db.test.ts`).
   - **Nothing by surprise.** A setting that keeps less or deletes more needs the counts that were shown (a fingerprint over the setting, the cut-off day and the counts, checked again on the server), the typed name for a delete, and waits 7 days in which it can be cancelled. The job takes no more than the confirmation counted: the cap (`retention_cap`) holds the old backlog, and what earlier runs took counts against it, so values that arrive for periods already cleared cannot make room for more. A Retention without a confirmation on record is never run.
   - **Delete only after a check.** A span is condensed in two steps: the Condensed Value, then every Display Period at or above it recomputed from the originals with the code the widgets use and compared exactly. Only then does one database transaction remove the originals, under the Metric's row. It refuses unless the very Condensed Value is still there, the number of originals is the one counted, and no open work (Question, Task, Correction waiting for a decision, Approval, unfinished Workflow state) holds a period. A Condensed Value whose originals are gone is never taken back. A Metric's day is claimed once, with a lease.
   - **Refusals everywhere.** A value for a condensed period is refused by a database trigger (code `ZF446`), so the form, paste, Import, the API (409 `period_condensed`), Feeds, Workflows and Corrections cannot write into it. A value for a period that was deleted is not refused (deleted periods are not recorded); the cap holds the Metric back for a new confirmation.
   - **What leaves the server.** Condensed Values are sealed like values and read only for Metrics a person may see. The Metric given to browsers, View Links and Snapshots carries no Retention, pending confirmation or cap. The download before a delete is for those who may set the Retention, is checked for a same-site request, is neutralised against spreadsheet formulas, is limited in size and is written in the Audit Log in counts. The Audit Log and the job's notes hold counts, days and words, never a value.
   - **The job route** opens only with the job secret, compared in constant time, and answers 404 to everyone else; it reads no input. The demo is skipped and its tables refuse writes; the rows go with a deleted trial.
   - **What it does not promise.** Backups keep deleted values as long as the Installation keeps backups, and Snapshots, decks and View Links keep what they showed (see accepted risks).
22. **Checklist Items and Send Snapshot (spec 0045).** Two Workflow steps that send things to people once per period, and a Task about no Metric.
   - **Send Snapshot is a way numbers leave the Workflow owner's hands,** so it sends a link and nothing else: the message holds no value, no Metric name and none of the Snapshot's words, and the recipient opens the Snapshot signed in, where `forReader` shows only the Metrics they may see now. The step never makes a Share (that would show every Metric on the dashboard) or a View Link (that shows the whole Snapshot to whoever holds it). Each recipient is checked when the step runs and again when the message leaves (`archivedMetricHolds`) for whether they may open the dashboard, are still a member and did not say "stop telling me"; one who may not is skipped and named to the owner only. A message whose dashboard or Workflow was deleted while it waited out Quiet Hours is not sent (`send-snapshot.db.test.ts`).
   - **The Snapshot is the owner's word.** It is taken and shown in the Workflow owner's name, only while they still own or edit the dashboard and see every Metric on it (`mayTakeSnapshot`, checked when the step is saved and when it runs). A draft someone wrote in is never shown over their words (`show_untouched_snapshot`, one statement). It goes once per period (the claim in `workflow_step_runs`, ids and counts only); unlocking and locking again, or reopening a Task, sends nothing more.
   - **Who chooses the recipients.** Only the Workflow's owner, in the app. A key or assistant never reads or changes the Send Snapshot step (the API leaves it out and keeps it as stored); the people of a Checklist Item are changed only with `workflows:people`, and a key without it sends them back exactly as read. Others reading the Workflow see an item's words only where they may read it (`mayReadItem`), never who it goes to, and the step's dashboard only when they may open it. When a person leaves, they are taken out of every Checklist Item and Send Snapshot step, so being invited again later does not put them back on either. That is done right after the handover, only over the config it read (an owner's save in between is not undone), and a failure is logged rather than undoing the removal; whatever happens there, nothing is sent to someone who is not a member, and every save drops non-members from the steps.
   - **A Checklist Task has no Metric to decide who reads it,** so nothing falls back to "everyone who sees the Metric": its people (Assignee, Stand-in, whoever it was handed on from while still a member, the asker) read it, Owners, Admins and Members otherwise, or only the people of its item's read Group, and a Guest only a Task they are on (`threadReader`, `checklist-visibility.db.test.ts`). The Schedule, the Calendar Link, the Actions page, the API, the MCP Server and the Period Timeline use that one rule. It is never sent to a Webhook (`queueWebhookEvent` drops Action events without a Metric).
   - **Checklist words are Workspace text.** They are plain text (no markup, links or line breaks, bidi and zero-width characters removed), at most 500 characters, sealed in the config at their place; one that does not open drops its item instead of running as ciphertext. Assistants get them as data, never as instructions (the MCP Server's instructions say so). Workflow Templates, Packs and Workspace Exports carry an item's words and days, never who it goes to, who ticks it off, its read Group or the Send Snapshot dashboard; a team template leaves out an item kept to a Group, and an export leaves out items its Owner may not read.
   - **The demo** shows a finished period from seeded rows; no step sends from the demo, and its tables refuse writes.

23. **Filled-in Values (spec 0046, #800 to #803).** A value one person enters in someone else's name, recorded and counted as the submitter's. The danger is a number put in a person's mouth, so it is kept honest four ways: the mark on the value, the Audit Log row, the message to the submitter and the Approval exclusions.
   - **Who may, decided once.** `mayFillIn` (`fill-in-rules.ts`) is the only rule, asked again from facts the core reads itself for every way in (`fill-in-check.ts`): `fillInValue` for the Metric's owner and the Workflow's owner (who must also see the Metric), and the Stand-in's answer to a Prompt sent in someone's place (reply, Slack, Telegram, form link, Record a value). Never an Access Key, so neither the API nor the MCP Server; never a Guest, oneself, a Feed, the demo, a locked or condensed period, a period that has a value, a Derived or Archived Metric, or "add up" and "keep both". Being an Owner or Admin opens nothing by itself. Only after the Due Date, or while the submitter is Away. The browser sends only the Metric, the period, the person and the text typed; the "Fill in for …" button is drawn from the same rule (`fill-in-offer.ts`), so it never offers what the core refuses.
   - **The Stand-in Token is narrowed.** A Stand-in's Token takes values only for the periods Ziffr asked them about, known from `prompts.stands_in_for` and never guessed from the Tokens, so someone who both submits and stands in records each answer under the right name; never through an Access Key; and the same holds for a late value in a locked period, which becomes a proposed Correction only for an asked period and never by key (#803). A Guest can no longer be chosen as a Stand-in; one chosen before records their own value, as before.
   - **Away is global,** so it opens filling in only when the person set it or an Owner or Admin of the Metric's Workspace did (who set it is kept on the Away row and asked at the time of entering); who set it goes into the Audit Log row.
   - **The mark goes wherever a submitter is named:** the Period Record, the Period Timeline and `period_status`, the Metric's History tab, the widget's history panel, the Changes page, the API's and MCP's `entered_by`, the Usage page's count and the Workspace Export. Names follow the existing rules for submitters: a Guest is shown neither who submitted nor who entered (the API gives a Guest's key `null` for both), a Metric the viewer cannot see stays a count, and the import's sealed `entered_by_name` shows only on the Metric page and never to Guests. View Links and Snapshots carry no submitter at all, so no `entered_by` either, with and without Show names (`fill-in-visibility.db.test.ts`).
   - **The Audit Log** (Owners and Admins) records `value.filled_in` with the period, for whom, in which role and who set the Away that opened it, never the value; the page names the person it was entered for (#803).
   - **The submitter is told** once (`filled_in`, held by Quiet Hours, also while Away): the Metric, the period, the value and who entered it; a Guest or a Contact reads "a colleague", and a Contact gets their form link instead of a page. It is checked again when it leaves: still their own Token, still sight of the Metric, the value still the filled-in one (not replaced meanwhile), and a message naming someone never goes to a person who became a Guest. They may replace it with their own until the Lock; the Filled-in Value stays in the history with who entered it.
   - **Nobody approves a value they entered or one entered for them,** through named Approvers and through the owner fallbacks; a Self-check goes to the submitter, never to who entered it, and "count it" without Approval does not apply to a Filled-in Value. A Correction to it is not decided by whoever entered it.
   - **Accepted.** An Owner or Admin can still open filling in for themselves in two audited steps: take the Metric over (#798, `metric.handed_over`, the old owner is told) or set the submitter Away (`away.set`), and then fill in (`value.filled_in` names who set the Away). Both leave rows in the Audit Log and the submitter is told of the value. A Stand-in's late value for an asked period that the Metric's owner locked while it was still empty becomes, once the owner accepts the Correction, a value in the Stand-in's own name, as every accepted Correction for an empty period is in its proposer's.

### The shared demo that visitors may change (spec 0051, ADR 0016)

Only on a demo-only Installation (`ZIFFR_DEMO_ONLY=1`) and only where `ZIFFR_DEMO_CHANGES` is on (off by default). Everywhere else the demo is read-only as before and none of this applies; with the setting off the database refuses every visitor's write as it always did. The entries below say what could go wrong when anonymous strangers may write into one shared Workspace, and what holds.

**What we protect here**

- **The Installation's other data.** A demo-only Installation holds no real Workspace, which is the first line of defence: nothing a visitor reaches is anyone's real number. The setting does nothing on an Installation that has real Workspaces.
- **Other visitors**, who must not be shown anything harmful or deceptive for longer than a reset window, and must not be locked out by one person.
- **The demo's examples** (the showcase and the seed's words), which the landing page, the sign-in page and the tour promise.
- **The server and its box:** CPU, database size and WAL, and the locks the demo shares with nothing else.
- **People outside the demo:** nobody may be messaged, called, linked to or made to fetch anything through it.
- **The reputation of the demo's address,** which a stranger's words on it can harm.

**Who attacks it**

- **A curious visitor** who types something rude, a lie about Ziffr, or a slur, into a name, a Question or a reply that the next visitor reads.
- **A script** that mints visits (the cookie is 128 random bits and free to make) to fill, slow or lock the demo.
- **Several networks** acting together, enough to use up the whole demo's budget for a window.
- **A visitor who tries to go further:** to another Workspace, to a table the demo keeps closed, to send something, to see what a made-up person such as the Guest may not see, or to change what the landing page promises.
- **A page left open** across a reset, or a request racing the reset.

**Residual risks the owner accepted**

- **Strangers' words are visible to the next visitors for up to 15 minutes.** The rules keep them short, plain and link-free, the seed's words and the showcase cannot be defaced, and the demo starts fresh when anyone changed it. Whoever reads them is a visitor of a demo that said so on every page. The levers if abuse shows are a shorter window, the check against bots (Turnstile, spec 0051 ticket 12, not built), a lower budget, or switching the setting off.
- **A visit id is free to mint.** A script gets a fresh per-visit budget with every request; only the address, network and whole-demo counts hold against it. The demo's own address key keeps those counts unreversible.
- **Several networks can lock the demo's changes for a window.** With eight or more networks (an IPv4 /24 or an IPv6 /48 each), the whole demo's 3,000 changes can be used up, and the demo is read-only until the next reset. Nothing else is hurt: reading is never limited and the window ends in at most 15 minutes. If it is used against the demo, a lower per-network share or the check against bots is the answer.
- **One person at a shared address (an office, a mobile network) can be refused by another's use of the same address's budget.** The refusal says so in plain words and ends at the reset.
- **Anyone may act as any of the demo's made-up people**, the Owner included (as before).
- **No check against bots.** Turnstile before a visit's first change was planned and not built (the owner decided on 2026-11-24 to rely on the limits first). The limits are the protection.

**What was independently reviewed**

Each pull request of spec 0051 that opens or protects something for anonymous writers was reviewed for security (the guard, untrusted input, locking, visibility), with fixes in the pull request itself. The record is in the pull requests: the visit's id (#985), the setting and the allow-list (#1007), the limits (#1020), the seeded words and the showcase (#1022, its fixes are the commits headed "Showcase: fail closed, jsonb words, dependencies, key changes"), open dashboards (#1044), open decks and Snapshots (#1052) and open Metrics, Threads and sharing (#1054). The first opening, values (#1046), carries fixes for input checks and per-address shares but no record of a separate review in its pull request; the whole spec, and the opening tickets in particular, still need the independent review of ticket 13 (#984) with the setting on in a running demo before it is turned on anywhere that matters. That review is not part of the pull request that wrote this entry.

## Gates in CI

- **Secrets.** `gitleaks` scans the whole history on every pull request.
- **Dependencies.** `pnpm audit --prod` fails on any known-vulnerable production dependency. Ignored advisories are listed below, each with its reason.
- **Client imports.** Client components may import only the core's pure modules, and CI's production build fails if the database module is bundled for a browser.
- **Database access from the app.** Outside sign-in, the session refresh and the demo, no file in the web app may import a database module or a Supabase client, or query the database (`.github/scripts/app-db-access.mjs`).
- **Core against a real database.** `pnpm --filter @ziffr/core test:db` runs every operation's permission tests against Postgres with the migrations applied.
- **The API, the SDK and the MCP server.** The route handlers are tested over HTTP against the same database; the app is then built and started, and the SDK and the MCP server are tested against it. The OpenAPI document must validate and match the route handlers, and the committed reference must match it.

## Accepted risks

- **A Metric's slug is not sealed and is made from its name** (spec 0028 step 2, ticket #248). A Metric's slug is its name in lower case with dashes, kept in clear because URLs, formulas and programs use it and the database joins on it (the spec lists slugs among what stays readable). Someone holding a database dump can read a Metric's name from its slug, so sealing the name protects it only where a person chose a slug of their own wording or the name is shown nowhere else; the dump test does not look for slugs. Opaque slugs would break formulas, URLs and API clients that name Metrics by slug, and are an open question (ticket #248).
- **Blind indexes show equal Contacts and equal labels within a Workspace** (spec 0028). A Contact's address and Slack handle are sealed, and kept unique by an HMAC of the normalised value under a key derived from the Workspace Key; a Breakdown row's label is sealed and found again by the same kind of index (so "add up" can merge rows). Someone holding the database sees which Contacts of one Workspace share nothing and which would clash, and which rows of one Breakdown carry the same label (history keeps none), never what the label says; across Workspaces and columns the indexes tell nothing. A label guessed from a short list of likely ones (a country, a month) could be confirmed only by someone who also holds the key, which the index is made with. Until the re-encryption job (#247), a period that still has plain rows is matched by a lower-cased label that the core sends to the database for that one call; it is not stored.
- **Demo visitors choose who they are.** In the demo anyone may act as any of its made-up people, its Owner included. Nothing there is real, and nothing reaches real workspaces (ADR 0005).
- **In a demo that visitors may change, strangers' words stay up to 15 minutes, a visit's id is free to mint, and several networks can use up its changes for a window** (spec 0051, ADR 0016; the owner accepted each, see [the shared demo](#the-shared-demo-that-visitors-may-change-spec-0051-adr-0016)).
- **Any checked View Design on a slide.** On a dashboard a widget draws only a design its Workspace keeps, or its own copy. On a deck's slide, in a Free layout or in a template, anyone who may edit it can place any design that passes the checks, since a slide keeps the copy its widget had. A design is inert data that reads only its widget's own Metrics, so this skips only the Owners' and Admins' choice of designs, not a protection (spec 0024 security review).
- **The Workspace's designs go to every member's canvas.** Every page with a canvas sends the Workspace's View Designs (at most 100 of 64 KiB) to its members, not to Guests, View Links or Snapshots. They hold no values; sending names first and a body only when it is placed is open work if Workspaces collect many.
- **Workbooks are read in the browser by a library from its vendor.** Paste values reads a dropped XLSX, XLS or ODS file in the person's own browser with SheetJS (spec 0026), loaded only on that page, and sends only the cells' text, which the server checks like a paste. A crafted file therefore reaches only the machine of whoever drops it. SheetJS is its vendor's official tarball (from cdn.sheetjs.com), kept in the repository as `vendor/xlsx-0.20.3.tgz` and pinned by its hash in the lockfile, so installs and Docker builds never reach the vendor's address. `pnpm audit` and dependency updates do not cover a dependency installed from a file, so its releases are checked by hand in the quarterly simplification pass; a new release replaces the tarball, its sha512 checked against the vendor's.
- **An Alert limit's count can show that a Metric was deleted** (spec 0032). Every Alert of a person counts against their limits, also on a Metric they lost sight of, so that losing and regaining sight cannot pass a limit. When such a Metric is deleted its Alerts go with it and the count drops. The person learns only that a Metric they once saw is gone, which is low risk, and a count that left them out would let the limits be passed.
- **Counts can say that someone looked** (spec 0031). Anyone holding a View Link can raise that dashboard's count without limit, which only keeps it off the "not opened" list. An Admin who can see a dashboard that only one person opens can tell that person is using it, though counts hold no person. The lists go to Owners and Admins only.
- **Image paths skip the middleware.** Paths ending in an image extension are not seen by the middleware. Pages still check sign-in themselves, and View Link pages are only reached under `/v/`.

- **sharp** (GHSA-f88m-g3jw-g9cj, GHSA-rgj7-g3m4-5g8c, GHSA-wq5f-xc86-pv6w), a dependency of Next.js. Ziffr does not use `next/image`, and the image optimizer is switched off (`images.unoptimized`), so sharp never runs. Remove the exception when Next.js is upgraded.
- **image-size** (GHSA-5p2g-fcmc-qvqq, GHSA-w3rx-r6r6-pgpr), a dependency of pptxgenjs. Only its Node build uses it; Ziffr exports decks in the browser, whose build does not include it.
- **Away dates belong to a person, not a workspace.** An Owner or Admin of one workspace can change the away dates of a member who is also in another workspace. The effect is limited to who is asked for values; the dates are visible only to members of a shared workspace.
- **A prefix of an Access Key reveals whether it exists.** Looking up an unknown prefix returns sooner than a known one. The 256-bit rest of the key still protects it. Calls with an unknown key are not limited per key (there is none to count against); limits for them belong with the sign-in rate limits below.
- **Limits may be passed by a burst.** Counting and recording a call are not one transaction, so parallel calls can pass a few over the minute's or the day's limit. The limits are there to stop a flood, not to meter.
- **The Audit Log is written best effort.** Its event is written in the same request, right after the action. If that write fails, the action stands and the server logs the event's kind, so an event can be missing (spec 0008).
- **Some events are what the browser says.** Decks are exported in the browser, which then tells the core; a changed browser can leave that event out. Sign-ins are recorded in every workspace the person belongs to, so each of them learns when the person signed in.
- **A connected Slack workspace's admins are trusted.** Someone who can change a Slack user's email address or take over a Slack account there can get that person's Slack messages and answer them, Approvals included. That is the trust an Owner gives by connecting it; the guide says so.
- **Telegram reads bot chats, and each person's Telegram account is trusted.** Bot chats are not end-to-end encrypted: what Ziffr sends and receives by Telegram passes through Telegram's servers, which the Connectors page says next to the switch. A link proves an account when it is made; whoever later takes over that account gets the person's messages and can answer them, Approvals included. The guide recommends Telegram's two-step verification; an Owner who does not accept this leaves Telegram off. One bot serves every workspace of an installation, so any workspace's Owner can invite people to it; the bot names the workspace and person in every connection, and `/stop` ends it.
- **A Slack workspace connected elsewhere is named.** "Add to Slack" for a Slack workspace already connected to another Ziffr workspace says so, which tells that Slack workspace's admin that it is in use with this Ziffr. It names nothing of the other workspace.
- **The network address needs `ZIFFR_PROXY_HOPS`.** Without it Ziffr cannot tell a client's own `X-Forwarded-For` from its proxy's, so it ignores the header and only the per-address ceiling (30 links an hour) holds. With a wrong value a client could pick its network address; the per-address limits still hold.
- **CI actions are pinned by commit** (spec 0009); updating one is a reviewed change of its SHA. gitleaks is pinned and checksummed.
- **A leaked Feed Key can fill empty past periods without Approval** (spec 0012). Within its Feed's Metrics and daily limit, it can record Imports that no one checks. They are marked as imported and named by the Feed and its key, Locks still hold, and Owners and Admins see the Feed's calls and refusals. We accept this so that connecting history does not raise an Approval for every period.
- **A trial's Owner can pass on their own reach.** Whoever gets a trial Owner's Telegram start link or Slack code receives that Owner's messages. It takes that person's own action and reaches nobody new against their will (spec 0021).
- **A trial's Owner is who signed in, nothing more.** Anyone with an email address gets a trial; Turnstile and the limits make many of them costly, not impossible. A trial reaches nobody but them, so what they can do is spend the Installation's limits.
- **Typing a Tag can say that the word is used out of sight** (spec 0038). A word that exists only on Metrics a person cannot see is the same Tag Workspace-wide, so typing it attaches that Tag. The answer uses the person's own spelling, but every later read (the Metric page, the Metrics list, `GET /api/v1/metrics`, `list_metrics`) shows the Tag as it was first written, so the person learns that the word was used before and how it was spelt. The same holds for renaming a Tag to such a word (the two are merged), and at the Workspace's 200 Tags, where a new word is refused but one that exists is taken. None of them says where the word is used or on what.
- **Assistants read workspace text.** An MCP client puts Metric names, descriptions and values into an AI assistant's context, and text written to mislead it could make it misreport numbers or, with a key that may submit, record a value the person did not ask for. Such a value goes through the Metric's rules, names the key, and shows in the Access Log.
- **An assistant's name is its own claim** (spec 0023). Anyone can register an assistant called "Claude" with an https address of their own. The consent screen shows the name as a claim and the host the person returns to, which is the part an impostor cannot fake; for programs on the person's computer, where any program can use any port, it warns that the name proves nothing. Connecting stays the person's decision, with only reading ticked by default.
- **Holding a connection's token is holding the connection, for an hour.** An access token is a bearer token: until it expires, whoever has it acts as the connection at `/mcp`, as with any Access Key. Disconnecting, revocation, an Owner revoking, or the person leaving stop it at once, since every call checks the key.
- **Token, revocation and `/mcp` requests are not limited per network address.** Codes and tokens are 256-bit, so guessing is hopeless; a flood of wrong ones costs one lookup each, as with wrong Access Keys on the API. Registration and consent screens are limited.
- **Origin is checked only when sent.** Assistants call `/mcp` from their servers without an `Origin`. A browser page on another site sends one and is refused, and it would hold no token anyway.

- **Deleted values live on in backups and in Snapshots** (spec 0033). A Retention deletes values from Ziffr, not from backups (hosted Ziffr keeps them 30 days; a self-hoster's own) and not from Snapshots, decks and View Links that already show them. The confirmation says so. Only deleting a whole Workspace and destroying its key makes data unreadable.
- **A late value for a deleted period is accepted** (spec 0033). Deleted periods are not recorded, so such a value is stored; the Retention's cap holds the Metric back for a new confirmation instead of deleting it unseen.

## Open work


- **Sign-in links and the page's mail server.** Supabase Auth sends sign-in links with its own mail settings, so a mail server saved on the Installation settings page reaches everything but sign-in. Until Ziffr sends sign-in links itself, the server's settings still need a mail server for them.

- **Client ID Metadata Documents** for assistant registration (MCP authorization, revision 2025-11-25) are not offered: they make Ziffr fetch an address the client names, which needs protection against server-side request forgery first (ADR 0011).


- **A trial Owner who is the last Installation Admin** is kept when their trial is deleted, with their sign-in. Add another Installation Admin, then delete them by hand if they should go.

22. **Data at rest (spec 0028, ADR 0012).** What a stolen database dump, a backup or a read-only SQL leak shows.
   - **What is sealed, and how.** Spec 0028 gives every Workspace a Workspace Key, wrapped by a key derived from `ZIFFR_SECRETS_KEY` under a label of its own (HKDF) and destroyed when the Workspace is deleted; the keys exist since ticket #245 (`workspace_keys`, service role only, never a key in clear), and step 1 seals with them, column by column (#246): Thread messages, the text of Questions and Tasks, a Prompt's question, a period's Workflow note (Approval reasons, a send-back comment), a Slack connection's bot token (under the Workspace Key instead of `ZIFFR_SECRETS_KEY`, so it dies with the Workspace; one connected before is sealed again by the job), Contacts' names, email addresses, Slack handles and phone numbers, Breakdown labels, the Outbox (a Delivery's subject and text), the intake log (sender, raw text, outcome) the Audit Log's object names and details, a dashboard's introduction, a widget's title and a Finding's kicker, headline, subline, footnote and source, a Snapshot's words, and Metric descriptions are sealed on write (AES-256-GCM, bound to the Workspace, table, column and row) and opened on read; the copies of those words in Versions are sealed for the Version, a frozen View Link and a View Link to a Snapshot keep theirs sealed for the link, a Snapshot's frozen part holds no words, and no View Link or Snapshot carries a Metric description (#334); callouts and annotations of a Finding, text in a free layout, and the documents of decks and templates are not sealed yet; step 2 (#248) seals the numbers: values and the ones they replace (history), a Breakdown row's value, Target Series and Projections, a Metric's Target Range and name, the value a late Correction proposes, the data frozen in a Snapshot or a frozen View Link (sealed as one text, with only the ids of the Metrics it kept beside it, which the database checks who may open it by), the name and Target Range a Metric's Version keeps, and the Check percentage and a Tell step's level or share in a Workflow's settings; a number is sealed as text in a column beside its numeric one, bound to its row, and the numeric one is emptied, with a check that exactly one is set, so the database can no longer add values up and the core does it (the "add up" rule and Breakdown row merging read, add and write back, and the database writes only if the rows are as the core read them), and the checks that refuse a value for an archived Metric or a condensed period watch the sealed text too; rows written before are sealed by the same job, which tells the database a value is only being sealed, so that no history entry or refusal follows, and which also seals the data of older Snapshots and frozen View Links, the numbers of older Versions and Workflows and moves them with the key version (the database allows a Snapshot's frozen part to change only for that); a CI step dumps the test database and searches it for known words and numbers of a sealed Workspace (`.github/scripts/dump-test.mjs`), failing on any hit; rows written before are sealed by the re-encryption job (#247, `/api/jobs/workspace-keys`), a few hundred at a time, each written only if it has not changed since it was read, so it can stop, start and run twice at once; the job also fills in a Contact's blind indexes (a collision is held back and reported, never dropped) and moves rows to the newest key version. Once a column holds nothing in clear and every sealed value in it opens, the column is checked off for that Workspace and the core refuses plain values there, so clear text planted with database access reads as missing instead of being taken for data (members' own names and an event's details, which can hold either, are not enforced); the next daily pass seals it again. A sealed value that does not open is counted apart from plain ones and never overwritten. The words sealed inside JSON columns (Findings, Snapshots, Versions, View Links), Breakdown labels with their index and history, and a Webhook's external task with its hash are sealed by the same job (#250). Changing a Workspace Key (#250) adds a new version that is pending for 11 minutes (processes keep a Workspace's keys for 10, so every one holds it before anything is sealed with it), then takes over, and the job moves everything over; an old version is destroyed only 15 minutes after it was retired and only once no value or blind index refers to it, and a process that meets a value of a version it does not hold loads the keys again. Changing it does not make a dump or backup from before readable less: that copy holds the old wrapped key. The Audit Log stays add-only except for one function the job uses, which can only change an event's name and details from plain to sealed text (or to a newer key version) and nothing else. SQL-made rows (the demo, a trial's seed) stay in clear too. Deleting a Workspace (today: a trial) destroys its key before its rows (#249), until its rows are gone the Workspace stays marked so that no new key replaces it, and the Installation's audit keeps its id, never its name. A backup from before the deletion still holds the wrapped key, which `ZIFFR_SECRETS_KEY` unwraps, so the promise is: unreadable in backups after the retention period. It will not protect against a compromised app server, the Installation's operator or a memory dump; running Ziffr yourself stays the answer for that.
   - **What it protects against.** A stolen database dump, backup or disk without `ZIFFR_SECRETS_KEY`; a read-only SQL leak; reading a deleted Workspace from the live database or any copy made after its deletion. Deleting a Workspace destroys its key first, and a Workspace that had a key is never given a new one in its place.
   - **What it does not.** A compromised app server or core process; a malicious operator; a memory dump of a running Ziffr (Node cannot promise to wipe freed memory, and unwrapped keys stay cached for up to 10 minutes per process); backups from before a deletion, which hold the wrapped key and open until they expire or the Installation key changes, so the promise is "unreadable in backups after the retention period"; and anything the operator keeps next to the database, such as a backup of `ziffr_keys` stored with the dump. It is not end-to-end encryption: Ziffr reads the data to do its work. Ziffr does not revoke a deleted trial's Slack token at Slack.
   - **The mixed state.** Rows written before stay in clear until the re-encryption job seals them, and the core reads plain and sealed rows alike; rows made by SQL (the demo, a trial's seed) are in clear. A value that does not open reads as missing, never as its ciphertext, and a Delivery that does not open is never sent. A Workspace whose key cannot be unwrapped, or is gone, is refused: nothing is written in clear in its place, and no Slack token is asked for. The demo has no key, and an Installation without `ZIFFR_SECRETS_KEY` works in clear as before.
   - **Losing `ZIFFR_SECRETS_KEY`** loses every Workspace's encrypted data. There is no recovery and no back door; it is the key to keep apart from the database.
   - **Owners** see one line under Workspace settings ("Encrypted with a key of its own. Deleting this Workspace destroys it.") and nothing more: no key, version or progress; Installation Admins see progress and versions, never a key.

23. **Personal Webhooks (spec 0037, #641 to #646).** A way out of the Workspace that the Admin allowed and one person points: an https address a person adds for themselves under You → Your Webhooks, acting as that person. Guide: [webhooks.md](../guides/webhooks.md#personal-webhooks).
   - **Who may make one.** Owners, Admins and Members, with their role read from the database at every call, and only while the Workspace's switch (off by default; Owners and Admins; turning it off pauses every Personal Webhook and drops what was waiting) is on. Not Guests, Contacts, Access Keys, assistants, programs or the demo. There is no API route, MCP tool or SDK function that creates, changes or points one anywhere, so a prompt-injected assistant cannot make one; a test lists the routes, tools and SDK files and fails on any mention (`personal-webhooks-surface.test.ts`). An Alert can name a Personal Webhook only from the page, never by a key.
   - **What it may carry.** `personalWebhookMayHear` is the one place that decides, with the person as the Actor and the core's visibility functions (the Metrics they see, who may read a Thread), at every send, not at the event: a Metric made private, a Share taken away, a Group left or a demotion between event and send means nothing goes out and the log says nothing. Action events only for Actions given to the person or asked by them; value events only for up to 50 picked Metrics that are not archived or Derived; the number of a `value.unusual` only where the person may see a value waiting for Approval. The message is the full one of spec 0034 and nothing more: no Breakdowns, Contacts, dashboards, Share lists or older Thread messages, and another person's email address is never in it. A Workspace Webhook still never gets a personal Alert; a personal Alert reaches only the person's own Personal Webhooks, up to 3, judged again at send (sight, Alert not paused and still naming the Webhook, value still meeting its condition).
   - **Status back.** Item 19 above: signed, only Actions sent to that Webhook, as the person, never an approval; the switch, role and sight are re-checked on every request and fail with the same 404. Its Thread lines and Audit Log entries carry the Webhook's name with its person's, so it cannot pass for or block a Workspace Webhook.
   - **Where it can reach.** The shared outbound request of item 18, unchanged, at save and at every send (no second copy of the rules). The operator's private hosts apply to a Personal Webhook, except in a trial (item 12), where they never do.
   - **Limits.** 3 per person, 1,000 sends per person per day, each send also taken from the Workspace's daily cap in one atomic claim, so one person cannot use more than their own share and the server's load stays under one number; a trial's are 2 Webhooks of both kinds and 200 sends.
   - **What the browser gets.** The person's page lists their own, with the address masked; the address and secret are sealed with the Workspace Key. The Admins' list shows whose, name, the host only (the person's own page shows a little more of the path),  events, state and last send, and the log's statuses and times, never a message. Server actions only call the core.
   - **The end.** A Personal Webhook, its queue and log go when its person is removed, becomes a Guest or Contact, or deletes their account (a trigger records the end in `personal_webhook_ends`; the core writes the Audit Log entry with its reason, scoped to the Workspace, and the sweep drains the rest), or when the Workspace is deleted. An Admin's removal tells the person and is audited; a failure switch-off tells the person, not the Owners.
   - **Accepted.** A Personal Webhook's name in the Thread and the Audit Log carries its person's name and the first characters of its own id ("To Do (Ann's Webhook 3fa9)", cut to fit the Thread's 80 characters), so no two Webhooks share a label, and the hourly limit and the repeat check count by the Webhook's id (`thread_messages.via_webhook_id`), never by the label; the label is the Thread's and the Audit Log's, never a proof of who. A waiting value of a Derived Metric is never sent through a Personal Webhook at all, which is stricter than the app (who may see an input is not who owns the Derived Metric). An unsigned request with a real Webhook id costs a few extra reads before the uniform 404, as item 19 says (#487).
   - **Also accepted** (review of the whole spec, #647). Picks a person has lost sight of stay on the Webhook and are never sent; they come back if sight returns unless the person removes them ("Remove the N Metrics you can no longer see", done on the server). A person cannot change a Personal Webhook while the Workspace's switch is off. An assignee or asker hears an Action on a Metric they no longer see, as the app lets the people on a Thread read it, and can answer it from outside too: status back asks the same question as the app (the people on a Thread read and answer it), never a second one. A person's own page shows a little of the address's path; Owners and Admins see the host only. The Admins' list also carries the owner's profile id, which they already know from the member list.
   - **Audit Log.** The switch on and off; added, changed (address or events), secret replaced, removed (by the person, an Admin, or because the person left), switched off after failures. Addresses appear masked, never a secret.

24. **Tags (spec 0038, #656 to #662).** Free words people put on Metrics (at most 10 on a Metric, 200 in a Workspace, 32 characters, plain text). A Tag is a row of its Workspace, but a Tag name says what the Workspace measures as much as a Metric name does.
   - **Seen only through a Metric.** One core function (`tagSight` in `tag-sight.ts`) decides what a person is shown of Tags: a Tag only when a Metric they may see carries it, with counts of those Metrics only. The suggestions while typing, the Metrics list filter, Search and `find`, the Tags page, `GET /api/v1/tags` and `list_tags`, every Metric read, the dashboard widget and Export as Pack all read it. A filter or a Search for a word that is not a Tag the person sees matches nothing, the same as a word nobody uses.
   - **A Tag never opens a Metric.** A widget of "all Metrics tagged X" draws, for each viewer, the tagged Metrics they see through their own role, Shares and Groups, never through the dashboard's Share; it stores no list, so the Share opens nothing through it, and an empty widget says the same whether the Tag is gone, unused or only on hidden Metrics. A View Link needs a fixed list (Fix the list, which says what it will show); decks, Snapshots and widgets inside free layouts record the Metrics of the person who made them and carry no Tag. A Dashboard Template names no Tag: a Tag widget becomes a Slot called "Tagged Metrics".
   - **Who may change what.** A Metric's owner and its Editors (directly or through a Group) put Tags on it; a Guest Editor only Tags they already see; a Viewer never. Owners and Admins rename, merge and delete Tags, for a Tag they see; that acts on hidden Metrics too, and the confirmation says only that there are some. A key never tags as itself: the API checks `metrics:write` (create) or `metrics:edit` (update) and then acts as the key's creator, and the core refuses a key's shape (`mayTag`). No API route or MCP tool renames, merges or deletes a Tag, since a prompt-injected assistant would be asked to tidy one away (`apps/web/src/app/api/v1/tags/route.test.ts`).
   - **Untrusted words.** Every name from a browser, a program or a Pack goes through one function (`@ziffr/pack/tag-names`, shared by the app, the API and `npx @ziffr/pack check`): NFC, white space collapsed, no comma, markup, control, format, private-use or lookalike filler characters. Names are compared in the core over opened rows, never in a query filter. Tags in a Pack are listed with the texts aimed at assistants before installing, and the MCP tools say that Tag names are the Workspace's words: data, not instructions.
   - **At rest.** The name is sealed with the Workspace Key from the day it exists, with a blind index of the lower-cased name for one Tag per name (spec 0028 step 1; the dump test looks for Tag names).
   - **Audit Log.** `tag.renamed`, `tag.merged` and `tag.deleted`, written from the actor's sight; another reader sees the Tag's current name, if they see it, and the kind of change, never the other name or the counts.
   - **Accepted.** See "Typing a Tag" under accepted risks.

25. **Automation Templates for Feeds (spec 0043, #769).** Files that go out of Ziffr and into someone's n8n, and a text that goes into someone's assistant. Ziffr runs neither, calls no other system, and holds no login for one. Guides: [Google Sheets](../automations/google-sheets-feed.md), [Stripe](../automations/stripe-feed.md), [HubSpot](../automations/hubspot-feed.md).
   - **Who may get a file.** Owners and Admins, through the app only: never a key, never a Member or Guest, never in the demo (`assertManagesFeeds`). Every Metric goes through `editableMetric` (the person may change who submits to it; a Derived Metric is refused) and the Feed must be a live Feed of the Workspace, all checked before a Feed is made. Adding the Feed to the Metrics, and the Feed Key, are made by the core's own operations and audited as any (`feed.template_downloaded` holds the template's id, a count and whether a key was made, never the file or the key).
   - **What is in a file.** The template as this repository ships it, with one value set in the parsed workflow: this Installation's address (`ZIFFR_SITE_URL`, never one from the browser). Nothing from a browser, a Pack or a Metric's name reaches the file's structure; a template is matched by id against the shipped list, never used as a path. The address must be https unless it is this computer, and the app refuses to make a file in production while the address setting is unset, so a key is never sent over plain http to a name on a network. A Metric's slug must be one the templates accept.
   - **The Feed Key is never in a file.** n8n keeps it in a Header Auth credential (`Ziffr Feed Key`); the page shows a new key once, beside the download, and it ends within a year. A file travels (it is emailed, committed, pasted), a key must not. A test refuses a key-shaped string in any template.
   - **What a key can do.** What any Feed Key can: write values for the Metrics its Feed submits to, and list them (`GET /api/v1/feed`), nothing else (item 5). A key made for an existing Feed works for every Metric of that Feed, not only those just named; the page says so, and a new Feed is the default.
   - **What a template sends and reads.** Only `{ metric, period, value }` goes to Ziffr: slugs are checked in the Code nodes, and no other field of a row, subscription, deal or contact is sent. Stripe is read with GET only and HubSpot with its read-only search; the guides ask for a restricted key and read-only scopes, and a test fails if a template writes to the other system. A list too long to add up fails the run instead of sending a number that is too low.
   - **Figures that are wrong without an error** were the larger risk, and are met in the flow: a past period that already holds a value is not sent again (the node "What is filled" reads the Feed's `filled` list, as `@ziffr/feed-kit` does), so a rerun cannot overwrite, add to or double it under any Submission Rule; the monthly figures are for the month that has just ended and the flow runs in UTC, so the month is the same wherever n8n runs; Stripe counts a cancellation on the day the subscription ended. What stays with the owner: last month has no value yet, so it is an Import and skips the Unusual Value check (the guides say so); a current-period value under an `add` or `keep_both` Submission Rule is counted each run (the Google Sheets guide says so).
   - **One skeleton, one contract.** Every Feed template is a source (read nodes and a `Figures` node that hands over plain rows) plus the same checking node (`code/feed-finish.js`: each row checked as Ziffr would check it, filled past periods left out, the key made from the figures). A contract test runs for every template listed in `feed-templates.json`, with one fixture each, so a new template cannot be added without it: it fails until the template has a fixture, and then checks that the shared node is word for word the same, that only `metric`, `period` and `value` leave, and that Ziffr is reached only through two nodes.
   - **The sender's side.** `POST /api/v1/feed/observations` answers every mistake a sender can make with a status and words that name the field (`sender-errors.db.test.ts`, 35 cases: keys, shape, numbers, periods, Idempotency-Key, limits, refusals by the Metric's rules), never a 500; the Feeds guide lists each answer and what to do. **Connectors → Send values** shows each member a call to copy for a Metric they see, with a placeholder where a key goes: the list comes from the core with the person's sight (`sendableMetrics`: only Metrics they see; a Feed Key's list for Owners and Admins, a person's own key's list only for Metrics they submit to; none for a Guest), and the text is built so a Metric's name cannot become part of a command.
   - **A Pack names templates by id only.** `feeds` in a manifest takes an id from the list Ziffr ships (an enum in the schema and a reference check, the same code in `npx @ziffr/pack check`), keys of the Pack's own entries and at most 10 items; a Pack never carries or links to a flow. Installing makes nothing of it, and Set up only offers the download to an Owner or Admin as above.
   - **The text for an assistant** is built in the browser from the Metric's name, description, unit and slug, which come from the Workspace: each goes in as one JSON string on one line, stripped of control, line-separator and direction characters and cut to a length, and the text says they are data and asks the person to confirm a table before anything is recorded. It holds no key, is never sent anywhere or run by Ziffr, and what the assistant records is recorded as its person, by the Metric's own rules. A description that tries to give orders still reaches the person's own assistant; the quoting and the confirmation step are the defence, and no text can make an assistant safe against a hostile description: accepted.
   - **Accepted.** n8n's run history keeps what n8n reads (HubSpot's one record, limited to its id; Stripe's subscription objects), as the owner's own n8n holds their other data. A downloaded file whose Feed is later deleted simply fails at Ziffr with a refusal. A failure part-way through a download can leave a Feed and some Submitter links made.

26. **Feedback filed on GitHub and answered (spec 0049, #915, #917, #918).** The first thing in Ziffr that posts a person's words on a public page for them. Hosted Ziffr only (`ZIFFR_CLOUD_KEY`); a worker (`POST /api/jobs/feedback`, job secret) files each Feedback whose status is `open` and has no post yet, through a bot account. Needs a security review before it is switched on.
   - **Personal data in the words.** The words are the person's own and public once filed; the form says so. Nothing is added from the person or the Workspace: the post is built from exactly five stored fields (kind, words, route, app version, an opaque reference) by one pure function (`feedback-bridge.ts`) that reads no other field of the row. The route is made plain on the way in (a Metric's slug or an id becomes `:name` or `:id`, no query, no address) and checked again before posting. A test feeds rows that carry an email, a name, a Workspace, a Metric and its value, and hostile words, and fails if any of it appears outside the words. What a person types about themselves or their numbers is theirs to choose; the review-first mode (a later ticket) is the control if it becomes a problem.
   - **Words that act.** Before posting, zero-width, bidirectional, tag and control characters are removed, `@mentions`, `#123`, `owner/repo#123` and `GH-123` are defanged (one invisible character after the `@` or `#`) so nobody is pinged or linked, the length is capped (2000 characters, title 80), and the words go inside a code fence longer than any run of backticks in them, so they cannot render as markdown, a link, an image or HTML, or close the fence. The title is one plain line of the words.
   - **Abuse and spam.** Per-person and per-Workspace daily limits (the store, #915); the worker files at most five per call, tries a feedback at most five times, ten minutes apart, and files nothing that waits for review. Done (#947): a daily cap for the whole Installation (default 200, setting `ZIFFR_FEEDBACK_PER_DAY`, 20 to 100,000), counted in the same transaction as the other two under a third lock taken after theirs; over it the person is told feedback is paused for today. Not yet: the review queue (#919). Accepted until then: a signed-in account can post its few words a day to a public repository.
   - **Link between person and post.** Only the `feedback` row holds it (`github_number`, `github_url`), in a table no browser role can read; the post carries the reference, which is random and not derived from anyone. The GitHub bot account is the only author. Timing can link a post to a person who sent one feedback at a quiet moment; accepted, and the form says the words are public.
   - **The bot token.** `ZIFFR_FEEDBACK_GITHUB_TOKEN` is read from the server's environment only, sent only in the Authorization header to `api.github.com` (no redirects followed, 15 second timeout), and never logged, stored or put in an error: a failed call records a fixed phrase ("GitHub answered 502."), never GitHub's answer. Give it the least it needs: Issues and Discussions write on the one repository. A leaked token lets someone post as the bot, not read any Ziffr data.
   - **Answers coming back (#918): the webhook.** `POST /api/inbound/feedback-github`, central version only. A body is believed only when `X-Hub-Signature-256` is the HMAC-SHA256 of the raw bytes under `ZIFFR_FEEDBACK_GITHUB_WEBHOOK_SECRET`, compared in constant time; without the central version's key, without the secret, or with one shorter than 32 characters the address answers a bare 404, a wrong or missing signature gets a bare 401, and the body is read only up to 512 KB (413 beyond). Nothing is parsed before the signature is right. The secret is read from the environment only and never logged or returned.
   - **Replay and redelivery.** Each handled delivery is claimed by its `X-GitHub-Delivery` id in a table (30 days), so a replayed or redelivered request changes nothing, and a comment is stored once by its own reference (a unique index), so the same comment under another delivery id is not added twice either. A delivery counts as handled only once its processing succeeded: a second request with the same id while the first is still running is answered with an error (so GitHub shows a failure and it can be redelivered), a failed one is given back, and a claim that crashed is taken over after two minutes. An edited team comment updates the stored words and a deleted one is replaced by "This answer was removed." (by reference, team messages only, the same plain-text rules). A removal is final (`removed_at`), and an edit is applied only when the comment's own `updated_at` is newer than the stored one, so a late or replayed edit can neither bring back a deleted answer nor undo a later edit. A signed request can still be replayed within GitHub's own rules by someone who recorded it, and then only repeats what GitHub did.
   - **Forged and foreign events.** A signature proves GitHub sent it, not that it is ours: the repository in the event must be the configured one, the event and action must be one of the few listened for (comment created; issue or discussion closed, reopened, answered), a comment on a pull request is dropped, and an event is mapped to a feedback only by the post's number and kind in our own store, so an unknown or other-kind post is a no-op. Every field read is checked for its shape.
   - **Who counts as the team.** Anyone may comment on a public post, and a stranger's words must not arrive under "The Ziffr team" with a notice. Only a comment whose author association is owner, member or collaborator is taken (`TEAM_ASSOCIATIONS`); a comment by another bot (a stale-bot, a CI notice) is dropped, and so is one of our own relayed replies (never echoed back). One account may both post and answer (the repository owner's): a comment by the bot's login is a relayed reply only when its first line is the header "A Ziffr user replied:" and its very last line is the reply marker (`Reference: ziffr-feedback-<16 hex>-<message id>`, checked by `isRelayedReply`); every other comment by that login is judged by author association like anyone's (GitHub reports OWNER for the owner's account of a user-owned repository, MEMBER or COLLABORATOR in an organisation; the accepted set stays owner, member, collaborator; a member whose organisation membership is private is reported as CONTRIBUTOR or NONE and is ignored). The retry's search for an earlier try of a reply applies the same test, so a team answer that copies the marker line is never taken for a pending reply and becomes a team answer. The marker cannot be forged by a person: their words are neutralised and fenced inside the comment, the marker is appended by the bot after the fence, so words with a marker in them never end the comment and cannot make a later team comment vanish; a team comment that quotes a marker anywhere but as its last line is an answer. Only someone who can write as the account could write a comment shaped like a relayed reply to hide it, and that someone is the team. The bot's own filed posts are issues and discussions, not comments, and are never read as answers. Everything else stays on GitHub. Needs a security review: this decides who may write into a person's conversation.
   - **A team comment that contains links.** The words are stored as plain text and shown as plain text: never rendered as markdown or HTML, never turned into a link, control, zero-width and bidirectional characters removed, capped at 2000 characters. A link in them is text a team member chose to write; the person may copy it. The notice to the person carries no words at all, only that there is an answer.
   - **Team answers are anonymous too.** The commenter's GitHub login is read only to tell the bot, other bots and the team from strangers and is never stored, logged or shown; a test proves the stored message and the event carry no login. A failed handling logs a fixed phrase, never the words.
   - **The notice.** Told through the same notice Tasks and Questions use, in the Workspace the feedback was sent from and only while the person is still a member of it, at most one an hour per feedback. The notice (and so the Workspace's Outbox, which Owners and Admins can read) shows the fixed sentence "The Ziffr team answered your feedback" and the person as its recipient: a Workspace admin can therefore see that someone in the Workspace sent feedback and got an answer, never what was said. Accepted for now; the alternative is a notice outside the Workspace's Outbox.
   - **Going out: a person's reply.** Stored by `replyToFeedback` (own feedback only, the words cleaned and capped at 2000 characters, five a day per feedback, fifteen a day per person, a hundred messages per conversation, counted under a lock) and posted by the same worker as the filing. The comment is built by one pure function from the words, the reference and the message id (the words neutralised and fenced exactly as in the post: mentions and references defanged, invisible characters removed, unbreakable fence), headed "A Ziffr user replied:". Only an open or answered feedback takes a reply (the core says so in plain words and the database checks again), and the worker skips the replies of a feedback that has since closed or is not open, so nothing queued before a closing or a review is posted unreviewed. The worker claims and posts one reply at a time under a 15-minute lease and a 60-second budget per call, so a slow GitHub cannot make two runs post the same reply; a try after an earlier one searches the bot's comments for its marker before posting; at most five tries, the row keeps a fixed phrase. A person can still say anything public in their reply: as with the first words, the form says it is public.
   - **Posting twice.** A claim in the database marks each try (a lease, two workers never take the same feedback), the post is recorded only where none is recorded, a unique index refuses one post for two feedback, and a try after an earlier one searches GitHub for the reference before posting. The search accepts only a post authored by the bot (its login asked of GitHub with the token, once) whose very last line is the reference, and takes the oldest, so quoting a marker in a post or in one's words cannot link a row to someone else's post. GitHub's search lags behind a new post, so a retry waits ten minutes; if the search still misses, a duplicate is possible and accepted (a maintainer closes it).

27. **Learning about a person or business through the Setup Guide (spec 0052, #991).** The guide asks for the Workspace Profile (industry, whom it sells to, country, size, revenue) and each person's Business Function, and keeps the state of its steps. Guide: [Getting started](../user-guide/07-getting-started.md#the-setup-guide).
   - **Nothing leaves the Installation.** The answers, the Business Functions, the guide's state and the Pack ranking are read and written only by the core, in this Installation's database. The guide makes no request to Ziffr's makers, Ziffr Cloud, the Marketplace or anyone else and records no telemetry: its only trace is the Audit Log lines below. The ranking (`pack-ranking.ts`) is a pure function of keys and is never stored. Using the answers centrally (analytics on ziffr.net, ranking Marketplace Packs by sending them) is out of scope and would need its own ADR. The words shown where people are asked are one text (`privacy-statement.tsx`), repeated in the user guide.
   - **Who sees a Business Function.** The person (`myBusinessFunction`, no person to pass) and the Workspace's Owners and Admins (`businessFunctions`), nobody else. A Member, a Guest, an Access Key and the demo get nothing, and the membership is read again, so a role claimed on the Actor but not held, a person demoted to Guest or one who left gets nothing and is not listed. The tables (`business_functions`, `setup_guides`, `setup_guide_people`) have row level security on and no grant to a browser's role, so only the core's service role reads them, and the person's row is deleted when they leave (a trigger on memberships). Owners and Admins see functions on Members and Groups, in the Team step (its "suggested: Ben (Finance)" is built only for them) and in the Audit Log (the old and the new key); the privacy statement says so where the question is asked. No page a Member or Guest reads, no API route, no MCP tool, no Webhook, View Link or Snapshot carries one.
   - **The Export leaves them out.** The Workspace Export reads a fixed list of tables (`workspace-export.ts`) and its header holds the Workspace's name, time zone, year start and Attainment method: no Business Function, no guide row, no Workspace Profile, no Test Message record. A View Link and a Snapshot are drawn from a dashboard's own Metrics and never read these tables. `setup-guide-privacy.test.ts` fails when the Export, the API, the MCP Server or the SDK names a guide or function table, a profile answer or a function.
   - **Cross-Workspace and untrusted input.** Every call takes the Actor first and filters by its Workspace. A function, a step name, a Metric id and a Pack id are checked on the server: the function against the fixed list (`isBusinessFunction`; the table's CHECK accepts exactly that list), a step against the five names (a Member only their two), a Pack only by id against the bundled list (never a path or a query), the guide's Metric only when it belongs to the Workspace and the person may see it (`canSee`), and the profile by `checkProfile`. The return from "Add to Slack" carries a fixed outcome word from a list, never an address, and no `next` or `return` parameter is followed.
   - **What the browser gets.** The Slide-over's list carries step names and ticks of the viewer's own steps; a step's screen carries cards of states and words, never an address, a token or another person's link; the Setup line is drawn from counts. The Audit Log lines `person.business_function_changed` (keys), `setup.step_skipped` and `setup.finished` (step names) and `pack.installed` with `source: included` hold no name or address. The guide's ticks write nothing.
   - **Accepted:** an Owner or Admin can read every member's function, by design (it is what makes "who is asked for what" useful). A function is not sealed with the Workspace Key (ADR 0012): it is a key from a fixed list, not content, and sealing it is one change to the core's sealed-column list that changes none of the rules above. The demo has none of it: it keeps `tour.tsx`, `/setup` leads back to the dashboard and the guard refuses a guide row. A Member demoted to Guest keeps a `business_functions` row, which every reader filters out.

28. **Using Test Messages to message others (spec 0052, #991).** "Send me a test" makes Ziffr write to a person on that person's press: email, Slack or Telegram. It is built so that the only person it can reach is the one pressing.
   - **No recipient parameter.** `sendTestMessage(actor, way)` takes the way and nothing else. The recipient is the acting person; the address is the one Ziffr already keeps for them (the sign-in address they proved); Slack and Telegram reach only the account the person linked (or the Slack user found by their address). The way is checked against `email`, `slack` and `telegram`. A Test Message cannot be built from a Metric, a Contact, a Group or any text a browser sends.
   - **Fixed text.** The subject and the sentence are fixed. The only variables are the Workspace's name (whitespace collapsed, at most 80 characters, and `<`, `>` and `&` taken out) and the way. It asks for nothing and cannot be answered, so no reply is taken as a value.
   - **Refused** through an Access Key, in the demo, for a Guest and for someone who is no longer a member (the membership is read again). A way this Ziffr or the person lacks is not sent: it is kept in the Outbox, marked "Test", with a reason in Ziffr's own words (`shownReason`: a mail server's or a provider's text never reaches the browser).
   - **Limits, claimed in the database.** At most 3 by one way in 10 minutes and 20 a day by all ways together, per person in a Workspace; 5 a day in a Trial Workspace, so tests cannot use up the trial's messages a day. `claim_test_message` counts under a per-person advisory lock, so parallel presses cannot both take the last place, and says which limit and when it resets. Rows older than a day are deleted. Quiet Hours do not hold a Test Message: it is the one message that goes out in them, and only to the person who asked for it.
   - **Ask me now and Ask me for it** (the First Metric step) send the person's own request to the person and nobody else. **Ask me for it** makes the actor a Submitter of the guide's Metric, only when they own it, through the one operation that adds Submitters, and is held to the ten minutes of Ask me now per Metric and to the same daily cap as Test Messages (20, 5 in a trial; it claims a place in the same table).
   - **Audit.** `connector.test_sent` holds the way and the outcome (sent, waiting, kept), never an address; the Audit Log shows it to Owners and Admins.
   - **Fix paths:** an Installation without a mail server, Slack app or Telegram bot sends nothing and the Outbox says why; an Installation Admin adds or removes a way on the Installation settings page.
   - **Accepted:** the limits are per person and Workspace, so one person in many Workspaces can send more tests in all, each only to themselves (ticket filed). Ask me for it also uses places of the email window (ticket filed).

29. **Announcements (spec 0054, #1084).** One plain line that an Installation Admin writes and every person sees above every screen, and, when marked public, on the sign-in page for people who are not signed in. Guide: [Announcing maintenance](../guides/self-hosting.md#announcing-maintenance).
   - **What an Announcement can do.** Show words and one labelled link to everyone, including people not signed in when it is public. It runs no code, sends nothing and asks for nothing.
   - **Who can write.** Installation Admins only, checked in the core on every change. Admins of a Workspace will write only their own Workspace's Announcements later (spec 0054, tickets 5 and 6); this row is extended then. A Member, a Guest, an Access Key and a demo visitor cannot write one: the table is closed to the demo.
   - **Risks and answers.** Markup or script in the words: the text is plain, cleaned of control and direction-changing characters, 280 characters at most, and drawn as a text node, never as HTML. A hostile link: https only, parsed in the core (no name or password, 500 characters, never `javascript:`, `data:` or `http:`), the same rule as a CHECK in the database, a label always shown, and React refuses a `javascript:` address in a link. A flood: at most 20 on at once, counted in the same transaction as the write. A leak through the sign-in page: `publicAnnouncements()` is the only read without a person, takes only public rows that are on and in their window and returns only words, link and level, and a test fails if another column can reach it. The shell gets only id, words, link, level and whether it can be dismissed. Browsers have no direct grant on the table. Every create, change, switch and delete is in the Installation's audit with the actor and the words at the time.
   - **Residual risk.** A taken-over Installation Admin account can put a phishing link in front of everyone, and on the sign-in page in front of people who are not yet signed in. The answers are that few people are Installation Admins, the link is labelled and https, it is never opened by itself and every change is in the audit trail; an operator who suspects this deletes the Announcement and reads **Changes**. **Accepted:** the label is the admin's own words, so it can say something untrue.

30. **Using a Screen Link to message or lure someone (spec 0055, #1133).** "Send me the link" on a phone makes Ziffr email a person on that person's press.
   - **No recipient and no free address.** `sendScreenLink(actor, path)` takes a path and nothing else. The recipient is the acting person, the address the one Ziffr keeps for them, as for a Test Message (row 28). The path must be a whole match of one of the fixed screens (`desktop-screens.ts`): no host, other query, fragment or line break, at most 80 characters. The email therefore leads only to this Ziffr.
   - **Fixed words.** They hold the Workspace's name and the screen's name from the list, never a dashboard's, deck's or Metric's name, so a link to something the person may not see tells nothing; the screen checks that when it is opened.
   - **Refused** through an Access Key, in the demo, for a Guest and for someone no longer a member. No API route or MCP tool offers it.
   - **Limits.** It claims its place with `claim_test_message` as an email: 3 in 10 minutes and 20 a day (5 in a trial) per person in a Workspace, together with Test Messages by email. The Workspace's, the inbox's and the trial's mail limits count it like any email.
   - **Audit.** `connector.screen_link_sent` holds the screen's name and the outcome, never the path or an address.
   - **Accepted:** it is a notice, so with replies by email set up it carries a reply address like other notices; a reply records nothing. In the Outbox only the recipient sees it.

- **Breakdown parents (spec 0041, ticket 12).** A refusal never words anything about rows already stored (one generic answer for every sender); the words a sender gets are made of the rows it sent. **Accepted:** under the rule that adds values up, whether a value is refused or recorded still tells a sender who probes which rows (or how many, or how deep) are already there, one write per probe, as the rule's own answers (rejected duplicate, added) always told. The database guard and the core hold the same limits; a parent is named by label, never by id, so no id of another Breakdown or Workspace is ever accepted from a browser or a program.

- **Real Connectors.** WhatsApp and ticket systems are still simulated. Making them real needs signed webhooks, an allowlist of the addresses they call, and their own threat review, like email (spec 0004) and Slack (spec 0007) had.
